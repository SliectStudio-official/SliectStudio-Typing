## K-01 SQLite 事务回调拿不到数据库句柄

- 现象：`DELETE /api/admin/users/:id`、`DELETE /api/articles/:id`、`POST /api/user/error-log` 一律 500，错误文案为 `Cannot read properties of undefined (reading 'run')` 或吞成中文兜底文案。
- 根因：`db-config.js` 的 SQLite 分支在 `db.transaction` 里只执行 `await fn(...args)`，没有把数据库对象传进回调；MySQL 分支传了 `connDb`。而 `server.js` 的回调签名是 `async (tdb) => { tdb.run(...) }`。
- 位置：`db-config.js` 第 252-264 行；调用方 `server.js` 第 416、718、1120 行。
- 绕行：修 SQLite 分支时照 MySQL 分支的形状传对象，`server.js` 调用方不需要改；两分支必须对称检查。
- 会不会再踩：会。任何新增事务都要过这个函数。

## K-02 任意字符串经过时间归一化被截到 19 字符

- 现象：数据库面板编辑长文本字段后值被静默截断；实测公告内容写入后只剩 19 字；带字母 T 时首个 T 还会变成空格。
- 根因：`normalizeDateTimeInput` 无条件 `.replace('T',' ').slice(0,19)`，正则不匹配时**返回被截断的中间值**而不是原值；`parseDatabaseValue` 对所有字符串都调它。
- 位置：`server.js` 第 108-123 行；使用点 `/api/admin/db/:table/:id`（第 1506 行起）。
- 绕行：只有字段名属于时间列（`created_at` / `updated_at` / `start_time` / `end_time`）才走归一化，其余原样返回；正则不匹配返回原值。
- 会不会再踩：会。数据库面板是全表通用入口。

## K-03 请求体上限与内容上限自相矛盾

- 现象：40000 汉字的文章提交返回 413，响应是 HTML 错误页，前端 `res.json()` 抛 SyntaxError，用户只看到「网络错误」。
- 根因：`app.use(express.json())` 用默认 100kb 上限，而路由校验允许 `content.length <= 50000`（中文约 150KB）。
- 位置：`server.js` 第 34 行与第 580-582 行。
- 绕行：显式给 `express.json({ limit: '1mb' })`，并保证 413 也走 JSON 错误体。
- 会不会再踩：会。任何提高字段上限的改动都要同步请求体上限。

## K-04 排行榜同名列覆盖与匿名上报

- 现象：游客成绩读回时 `nickname` 为 null；任何人可匿名 POST 任意分数并冒用他人昵称。
- 根因：查询 `SELECT s.*, u.avatar, u.nickname` 中 `u.nickname` 与 `s.nickname` 同名，后者覆盖前者；`POST /api/leaderboard` 没有鉴权也不复算成绩。
- 位置：`server.js` 第 765 行、第 779-815 行。
- 绕行：起别名（如 `u.nickname AS user_nickname`）或 `COALESCE(s.nickname, u.nickname)`；上报侧至少要求登录并复算时长与字数。
- 会不会再踩：会。`SELECT *` 与 JOIN 组合时同理。

## K-05 鉴权只信 JWT payload

- 现象：管理员被降级为普通用户后，其旧 token 仍可访问 `/api/admin/*`；用户被删除后旧 token 仍能读写自己的数据；改密码不使旧 token 失效。有效期 7 天。
- 根因：`authMiddleware` 只做 `jwt.verify` 后把 payload 挂到 `req.user`，`adminMiddleware` 只判 payload 里的 `role`，全程不查 `users` 表，也没有 token 版本号或改密时间戳。
- 位置：`server.js` 第 172-191 行。
- 绕行：短时效 + 回查数据库取 role（或加 `token_version` 列，需先报 schema 变更）；两种修法都会导致全员重登，属待拍板项。
- 会不会再踩：会。任何新增受保护端点都继承这个语义。
- P9 之后的状态：改密 / 改角色都会让该用户其它 token 立刻失效（`token_version`）。**残留一处**：`POST /api/leaderboard` 是公开端点，只验签不比对版本，失效 token 仍能提交成绩（不能读数据），低危，见 ADR-0002。

## K-06 非生产分支落回硬编码 JWT 密钥

- 现象：快速启动（开发模式）下，任何读过源码的人都能伪造 admin token 直接拿到管理接口数据。
- 根因：`JWT_SECRET = process.env.JWT_SECRET || (isProduction ? '' : '硬编码值')`；而 `launcher.ps1` 的密钥文件 `launcher.config.ps1` 被 `.gitignore` 排除，不随发布包走，新机器默认落到开发分支。
- 位置：`server.js` 第 17-24 行；`launcher.ps1` 第 2 阶段。
- 绕行：任何模式都随机生成并持久化密钥，不给硬编码兜底。
- 会不会再踩：会。每台新部署机都会遇到。

## K-07 最后管理员可被降级，初始化接口对匿名重开

- 现象：把唯一管理员降为普通用户后，`/api/bootstrap/status` 返回 `needsBootstrap: true`，任何人都能匿名创建新的管理员账号。删除路径有「唯一管理员」保护，改角色路径没有。
- 根因：`PUT /api/admin/users/:id` 对 `role` 不做最后管理员校验；`/api/bootstrap/create-admin` 只以「是否存在 admin」为开关，且未限制来源；前端 `admin.js` 编辑用户时无条件回写 `role`（弹窗「取消=普通用户」），管理员手滑即触发。
- 位置：`server.js` 第 202-232 行、第 363-402 行；`public/admin.js` 第 764-769 行。
- 绕行：改角色时校验「降级后仍有至少一名 admin」；初始化接口限定本机来源或一次性口令。
- 会不会再踩：会。权限类改动都要问「最后一个管理员怎么活」。

## K-08 innerHTML 拼接与转义函数不完整

- 现象：注册时把 `email` 填成 HTML 片段会原样入库；管理员打开用户管理页即执行该脚本，token 存在 `localStorage`，等于全站接管。
- 根因：`escapeHtml` 只转 `& < >`，不转引号，且 `admin.js` 第 741 行把 `user.email` 直接拼进 innerHTML 未转义；服务端注册/改资料对邮箱无格式校验。属性拼接处（第 1219 行 `data-name`）同样受引号未转义影响。
- 位置：`public/admin.js` 第 741、1219 行；`public/script.js` 第 1306 行（转义函数本体）；`server.js` 第 234、301 行。
- 绕行：转义函数补 `"` 与 `'`；凡是插进 innerHTML 的字段一律过转义；服务端校验邮箱格式。
- 会不会再踩：会。三个前端文件都用同一套拼接风格。

## K-09 数据库面板下发 password_hash

- 现象：`GET /api/admin/db/users` 的响应里带完整 bcrypt 哈希，前端只是「客户端隐藏」，开发者工具或任一 XSS 可直接取走。
- 根因：服务端 `SELECT *` 后原样返回；敏感列过滤只做在 `admin.js` 的渲染层。
- 位置：`server.js` 第 1405-1455 行；`public/admin.js` 第 1021-1022 行。
- 绕行：服务端统一在返回前剔除 `password_hash` 等敏感列。
- 会不会再踩：会。新增敏感列时要同步这份名单。

## K-10 端口硬编码

- 现象：启动脚本检测到 3000 被占用会改用 3001 并设置 `PORT` 环境变量，但服务仍绑 3000，于是启动失败，脚本干等 60 秒报「Server start timeout」。
- 根因：`server.js` 写着 `const PORT = 3000`，从不读 `process.env.PORT`。
- 位置：`server.js` 第 16 行与第 1658 行；`launcher.ps1` 第 4 阶段。
- 绕行：读环境变量并给默认值；监听地址也一并参数化。
- 会不会再踩：会。多实例并行验证时需要。

## K-11 首次生产模式写配置丢密钥

- 现象：首次选择生产模式后，`launcher.config.ps1` 里只有模式没有密钥；第二次启动才补写完整，中间一次重启会让所有已登录用户掉线。
- 根因：首次写配置时只写了 `launcherMode`；补写分支的条件是「变量为空」，而变量在内存里有值，所以不触发。
- 位置：`launcher.ps1` 第 2 阶段（模式向导与密钥生成段）。
- 绕行：首次写配置就把模式与密钥一起落盘。
- 会不会再踩：会。只有全新部署会踩，最容易在交付现场踩。

## K-12 配置与版本各有两个来源

- 现象：`package.json` 的版本是 1.0.260706.2330-RE，`version.json` 是 2.0.260722.0240；`data/db-config.json` 是一份无人读取的旧配置（含 `active` 字段），`loadConfig` 只读根目录那份，而 README 写的却是 `data/db-config.json`。
- 根因：历史迁移留下的副本没清理，没有单一真值。
- 位置：`db-config.js` 第 4 行；`data/db-config.json`；`package.json` 与 `version.json`；`README.md`。
- 绕行：改任何「当前用什么配置/什么版本」的判断前，先确认读的是哪一份；清理需要用户批准（属待拍板项）。
- 会不会再踩：会。每次判断环境都会踩一次。

## K-13 静态资源无版本参数

- 现象：改了前端 JS/CSS 后，老用户的浏览器最长 7 天仍吃旧文件；Service Worker 缓存名是手工常量 `typing-practice-v7`，忘记改就永远命中旧缓存。
- 根因：`express.static` 对 js/css 设了 `immutable, max-age=604800`，而 HTML 里引用 `script.js`、`style.css` 不带版本参数（只有 `loading-indicator.js?v=2` 带）。
- 位置：`server.js` 第 44-47 行；`public/index.html` 第 29、337、338 行；`public/service-worker.js` 第 1 行。
- 绕行：发版时手工同步三处（引用参数、SW 缓存名、`version.json`）；本项未列入本轮修复范围。
- 会不会再踩：会。每次发版都会。
- **实证（P4 验收）**：执行方在已装 Service Worker 的浏览器上打开 `admin.html` 时，旧缓存的 `admin.js` 仍然执行了转义前的代码，页面真的执行了 XSS 负载；清缓存后才看到修复效果。也就是说**任何前端安全修复在缓存更新前对老客户端都是无效的**，K-13 的优先级必须高于其它前端项。

## K-14 删文章先删主表，成绩行清不掉

- 现象：删除一篇文章后，排行榜里出现标题为空的成绩行；成绩行没有被删除，只是 `article_id` 变成了 NULL。
- 根因：`DELETE /api/articles/:id` 的事务里先删 `articles`，再 `DELETE FROM scores WHERE article_id = ?`；而 `scores.article_id` 的外键是 `ON DELETE SET NULL` 且 `db-config.js` 打开了 `PRAGMA foreign_keys = ON`，第一步就把成绩行的 `article_id` 置空，第二步匹配不到任何行。
- 位置：`server.js` 第 716-726 行；外键定义在 `db-config.js` 建表 SQL 的 `scores` 段；`PRAGMA` 在 `db-config.js` 第 224 行。
- 绕行：调换两条 `tdb.run` 的顺序（先删 scores 再删 articles），不改 schema、不改外键。
- 历史数据：已有的孤儿行（`article_id IS NULL`）不要盲清——成绩上报本来就允许不带 `article_id`，只统计数量。
- 会不会再踩：会。凡是「主表带 SET NULL / CASCADE 外键 + 手工级联删除」的组合都要先想清顺序。

## K-15 字段名不一致导致静默回退

- 现象：管理面板「待审核文章」列表里作者永远显示「匿名」，即使投稿人有昵称。
- 根因：`admin.js` 读 `a.author`，而 `GET /api/articles/pending` 返回的是 `author_name`；变量取不到值时静默落到 `'匿名'`，没有任何报错。
- 位置：`public/admin.js` 第 500 行；`server.js` 第 625 行。
- 绕行：前端改用 `a.author_name`；更根本的做法是前端只消费契约里登记过的字段名。
- 会不会再踩：会。前端多处 `x || 默认值` 的写法会把契约不一致掩盖成「数据缺失」。

## K-16 编辑表单无条件回写全部字段

- 现象：管理员在「用户管理」里点某用户的「编辑」，只要在最后一个弹窗「是否设为管理员？」点了取消，该用户的 `role` 就被写成 `user`；对唯一的管理员这样操作会让全站失去管理员，并让初始化接口重新对匿名开放。

## K-17 通用数据库面板绕过入参校验

## K-19 Service Worker 模块级状态在重启后丢失

- 现象：只改了某个 js/css、重启服务后正常刷新页面，Cache Storage 里不会出现新的 `typing-<新版本>`，反而多出一个 `typing-fallback`，旧的 `typing-<旧版本>` 也没被清掉。
- 根因：`CACHE_NAME` 是模块级变量，初值 `'typing-fallback'`，只有 `install` 里调用 `resolveCacheConfig()` 才改成 `typing-<version>`；而运行期四处写缓存直接用这个变量。浏览器回收 SW 后重新拉起时不会重跑 install，模块状态回到初值，于是运行期写入落到 `typing-fallback`，下一次 activate 又把 `typing-<version>` 当旧缓存删掉。另一个前提：只改资源不改变 `service-worker.js` 字节，浏览器不会触发 SW 更新，install 根本不会跑。
- 位置：`public/service-worker.js` 第 1、13-26、198-212、214-228、258/284/304/317 行。
- 绕行：两条一起做——① 注册时把版本带进 URL（`navigator.serviceWorker.register('/service-worker.js?v=' + assetVersion)`），让资源变化能触发 SW 更新；② 不再依赖 install 赋值，改为每次 SW 启动都异步解析缓存名（所有 `caches.open` 调用前 `await getCacheName()`，结果记忆在模块内并带失效重试）。顺手删掉 `CRITICAL_ASSETS` 里遗留的 `/loading-indicator.js?v=2`。
- 会不会再踩：会。Service Worker 是会被随时回收的，任何「只在 install 里赋值、运行期当常量用」的模块状态都不可靠。

## K-22 PowerShell 脚本的两个坑

- 现象一：中文注释的 .ps1 一跑就报「字符串缺少终止符」「表达式或语句中包含意外的标记」，乱码满屏。
- 现象二：脚本里 `$major = [int]$Matches[1]` 突然报「无法将 Int32 的值 2 转换为 SwitchParameter」。
- 根因一：Windows PowerShell 5.1 读 **无 BOM** 的 .ps1 会按 ANSI 解码，UTF-8 中文被打碎，引号被吃掉。本项目的 `launcher.ps1` 首字节就是 BOM（`EF BB BF`），照它的做法写。
- 根因二：**PowerShell 变量不区分大小写**，局部变量 `$major` 与参数 `[switch]$Major` 是同一个东西，赋值即类型冲突。命名必须避开参数名（如 `$verMajor`）。
- 位置：2026-11-07 新增的 `set-version.ps1` 同时踩了这两个；已修。
- 绕行：写 .ps1 一律 UTF-8 带 BOM；局部变量避开 `[switch]` 参数名；改完先跑一次解析检查 `[System.Management.Automation.Language.Parser]::ParseFile(...)` 确认 errors=0。
- 会不会再踩：会。这两个坑都不会在编辑器里报错，只在运行时炸。

## K-23 自有版本号格式不是 semver

- 现象：任何「比较版本大小」「判断是否需要更新」的代码如果直接比字符串，就会把 2.10 判成小于 2.9；任何依赖 npm 语义的工具遇到这个号直接报错。
- 根因：本项目采用自有格式 `大版本.小版本.YYMMDD.HHMM`（见 AGENTS.md §4.3），它**不是** semver：四段式带日期段。
- 实测（2026-11-07）：`semver.valid('2.0.260722.0240')` 返回 null；`semver.gt` 抛 `Invalid Version`；`npm version patch` 退出码 1 并报 `npm error Invalid version: patch`；`npm pack --dry-run` 仍可正常打包。字典序排序结果为 `2.0.… < 2.10.… < 2.9.…`（错），按段数值排序才正确。
- 位置：版本真值 `VERSION`；写入口 `set-version.ps1`；派生文件 `version.json` / `package.json`。
- 绕行：① 任何版本比较必须按段解析成数字再比，禁止字符串比较（需要比较时先写一个 `compareVersion()`）；② 不要用 npm 的版本命令改版本，只用 `set-version.ps1`；③ 将来打 exe/msi 时注意 PE 文件版本每段上限 65535，而日期段 260722 已超，必须另定映射规则。
- 会不会再踩：会。「检查新版本」「公告里写请升级到 x.y」这类需求一出现就会踩。

## K-30 改了 public/ 不重启，资源指纹不变，浏览器与 SW 继续用旧缓存

- 现象：本地文件已修好、`curl` 拉到的也是新代码，但浏览器里仍是旧行为（本项目这次表现为首页一直「正在加载」）。换一台干净的浏览器打开却正常。
- 根因：资源指纹（`?v=<hash>`）是在**服务启动时**算一次并缓存进内存的。改完 `public/` 的文件不重启 → HTML 里的 `?v=` 仍是旧哈希 → 浏览器与 Service Worker 认为`这个 URL 我已经缓存过了`，直接把旧的（坏）文件给你。新建的无痕窗口没有缓存，所以看起来是好的。
- 位置：`server.js` 的 `buildAssetHashes` / HTML 引用改写；`public/service-worker.js` 的缓存键含查询串。
- 绕行：**改完 `public/` 一律重启服务**；验收时先跑这条一致性检查，不一致就是没重启：

```
# HTML 里引用的指纹 必须等于 文件真实哈希
$html = (Invoke-WebRequest -UseBasicParsing http://localhost:3000/index.html).Content
$ref  = [regex]::Match($html, 'nav\.js\?v=([0-9a-f]+)').Groups[1].Value
$real = (Get-FileHash public\nav.js -Algorithm SHA256).Hash.ToLower().Substring(0,8)
if ($ref -ne $real) { '指纹未刷新，需要重启服务' } else { '一致' }
```

- 会不会再踩：会，而且**每次热改前端都会踩**。彻底解法是让服务按文件 mtime 失效重算（已列入下一批）。验收清单里要常驻上面这条检查。

## K-31 粘性层高度改了一个，另一层的 sticky 偏移就失准

- 现象：比赛页公告条只露出一半，文字被副导航压住，看不清也点不到关闭。
- 根因：三层都是 `position: sticky`，各自写死 `top`：`nav` 是 0/44px、`.sub-nav` 是 44px、`.announcement-bar` 是 **74px = 44 + 30**（按副导航还是 30px 时算的）。P11 把副导航改成 56px 后，正确偏移应是 100px，于是公告条落在副导航身子底下；再叠加 `z-index: 48 < 49`，就被彻底盖住。
- 位置：`public/style.css` 的 `nav` / `.sub-nav` / `.announcement-bar` 三处；另外 `index.html` / `profile.html` 还各有一份内联的同名样式，数值不同。
- 绕行（按用户 2026-11-08 的要求定稿）：公告**保持 sticky 常驻**，但偏移必须用变量算——把各层高度抽成 `:root { --nav-h; --subnav-h }` 并在断点覆盖，公告写 `top: calc(var(--nav-h) + var(--subnav-h)); z-index: 51`，**禁止再写字面量**；插入位置固定在 `.sub-nav` 之后；样式只留 `style.css` 一处。改 `nav` / `.sub-nav` 高度时必须同步改变量，否则同样的坑会再来一次。
- 会不会再踩：会。凡是「多层 sticky 叠罗汉」，改任何一层高度都会连带另一层失准；验收必须按**断点逐档看**，不能只看一种宽度。

## K-32 分段时 trim 掉的空白，让「打字正文」比原文短，按原文索引的逻辑全部错位

- 现象：练习进度最多到 96% 到不了 100%；错字记录标错位置；朗读跳词。

- 位置：`public/script.js`（821 / 928-931 / 853-860 / 529 行）；比赛侧 `room.charCount` 用原文长度。
- 绕行：把「打字正文」定为唯一索引基准——`typingText = segments.join("")`，进度分母、字符状态、错字期望字、朗读定位全部改用它；原文只用于展示字数与难度。比赛侧建房时上报打字字数并由服务端校验范围。**不要试图让服务端复算**：实测「去换行+去行尾空白」与算法结果不等（272 vs 270）。
- 会不会再踩：会。任何"分段/净化后文本与原文并存"的地方都要先问：索引基准是哪一个。

## K-33 未匹配的 `/api/*` 返回 HTML 错误页，前端把 HTML 原文渲染给用户

- 现象：点「快速匹配」后，房间里出现一整段 `<!DOCTYPE html>…<pre>Cannot POST /api/race/match/join</pre>`。
- 根因：① Express 没有 `/api` 前缀的 404 兜底，未知接口走默认 HTML 错误页（**违反契约 §5「错误一律 JSON」**）；② 前端把 `res.text()` 原样塞进 DOM，连 `<pre>` 都渲染出来。

## K-42 `git push` 报 SSL certificate problem（本机证书链）

## K-46 局域网 http 下 Service Worker 不启用；客户端安全软件会 reset PUT/DELETE

- 现象一：以为“旧 SW 在作祟”，结果浏览器控制台里 `navigator.serviceWorker` 是 `undefined`。
- 根因一：SW 只在**安全上下文**（https 或 localhost）可用。本项目真实部署是 `http://192.168.x.x:3000`，因此 **PWA 离线能力在局域网部署下根本用不上**，`service-worker.js` 里的缓存逻辑只在开发机 localhost 生效。
- 现象二：管理页所有写操作报 `Failed to fetch`；`curl` 打同一地址的 PUT 返回 200。
- 根因二：**浏览器所在机器**的出站 `PUT`/`DELETE` 被安全软件或代理 reset（实测 `PUT /api/version` 这种不存在的路径也 `ERR_CONNECTION_RESET`，而 `POST` 正常返回 404）。与服务端无关。
- 排查手法（三条就能定性）：① 控制台 `fetch("/api/version",{method:"PUT"})` → RST 说明 PUT 被拦；② `fetch(...,{method:"POST"})` → 有状态码说明网络通；③ 服务器本机 `curl -X PUT` 打局域网地址 → 200 说明服务端没问题。
- 绕行：管理页写请求改走 `POST + x-http-method-override`（见 `docs/prompts/P41-写请求改走POST.md`）；或让用户在该机放行安全软件的 Web 防护。
- 会不会再踩：会。任何“PUT/DELETE 只在某些机器上失败”的场景，先做上面三条。
