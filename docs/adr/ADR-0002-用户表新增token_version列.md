# ADR-0002 users 表新增 token_version 列，实现改密/降权即失效

- 日期：2026-11-07
- 状态：已采纳
- 影响的版本：产物版本 3.0.x（数据规范不兼容 → 大版本递增）/ `CONTRACT_VERSION` 由 v1 → **v2**

## 背景

P3 把鉴权改成「每次请求回查数据库取 role」，解决了「降级/删号后旧 token 仍可用」。但留下一个缺口：**改密码不会让已发出的 token 失效**，攻击者拿到过 token 就能一直用到 7 天过期——用户改密码这个动作在最需要它生效的场景里等于没生效（坑库 K-05 残留）。

## 决策

1. `users` 表新增 `token_version`（SQLite `INTEGER NOT NULL DEFAULT 0` / MySQL `INT NOT NULL DEFAULT 0`）。
2. 签发 token 时把当前 `token_version` 写进 payload；`authMiddleware` 比对该值与库值，不一致即 401「登录已失效，请重新登录」。
3. 四个动作触发自增：改自己密码、改他人密码、改资料时带新密码、**改角色**（降权即失效）。自增与业务更新写在同一条 SQL 里，避免出现「密码已改但版本没升」的中间态。
4. 老库迁移靠 `runMigrations` 的 `ADD COLUMN ... DEFAULT 0`；**老 token 因此不会失效**（payload 无该字段按 0 处理，库值也是 0），不会造成全员重登。

## 后果

- 好的：改密 / 降权立刻踢掉该用户其它设备；不涉及改密的用户完全无感。
- 好的：不需要引入 token 黑名单表或 Redis，零新增依赖。
- 坏的：加列属**数据规范不兼容变更**，按规则必须升 `CONTRACT_VERSION` 与大版本，并同步本 ADR 与 §5.5。
- 坏的：降权时被降权者的会话会被强制中断——这是期望行为，但要在上线说明里讲清楚。
- 已知残留：`POST /api/leaderboard` 是公开端点，只验签不比对 `token_version`，所以失效 token 仍能提交成绩（不能读数据）。属低危，未在本批扩大范围。

## 替代方案

- **token 黑名单**：需要持久化存储与清理策略，收益与加列相同但复杂度更高，否决。
- **缩短有效期到数小时**：改密后旧 token 最多几小时内仍有效，且频繁重登影响体验，否决。
- **改密时直接删用户所有会话**：**当前没有会话表**，等于要先建会话体系，代价远大于加一列，否决。
