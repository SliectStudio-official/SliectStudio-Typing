# ADR-0001 版本号体系：两类版本、两个真值文件

- 日期：2026-11-07
- 状态：已采纳
- 影响的版本：`VERSION`（产物版本）/ `CONTRACT_VERSION`（数据规范版本 v1）

## 背景

项目前期版本号散在三处：`package.json` 写 1.0.260706.2330-RE、`version.json` 写 2.0.260722.0240、前端多处读后者、Service Worker 缓存名另有一套常量。没有任何一处是「唯一真值」，发版时必然漏改，用户与代理都无法判断当前跑的是哪个版本（坑库 K-12）。

## 决策

1. 版本号分两类，各自一个唯一真值文件：产物版本 → `VERSION`（格式 大版本.小版本.YYMMDD.HHMM）；数据规范版本 → `CONTRACT_VERSION`（格式 v 加整数）。
2. 产物版本递增规则：大版本＝数据规范/命令行接口/配置格式不兼容；小版本＝新增功能且向后兼容；每次构建刷新日期段 YYMMDD 与时间段 HHMM。
3. 写入口唯一：只允许 `set-version.ps1` 写 `VERSION`；同一分钟内重复构建直接拒绝写入，避免两个不同的包叫同一个版本。
4. 两类版本解耦：数据规范不兼容变更必须升 `CONTRACT_VERSION`，同时补 `AGENTS.md` §5.5 迁移说明并记一条 ADR。
5. 其余位置一律从真值派生，不得另立真值（含 `package.json`、前端显示、SW 缓存名）。

## 后果

- 好的：发版只改一个文件；「当前是什么版本」可一条命令复核（`set-version.ps1 -Check`）；静态资源指纹（P5 的内容哈希）与版本号互不干扰。
- 好的：数据规范与产物版本解耦后，「只改校验文案」不会被误当成规范变更。
- 坏的：迁移期存在派生文件滞后——`version.json` 与 `package.json` 的 version 暂时还需手工/脚本对齐，直到 P9 把服务端改为直接读 `VERSION`。
- 坏的：`package.json` 的 version 字段是 npm 语义要求的四段式之外的格式，需在 P9 决定「留空 / 同步 / 单独命名」。

## 替代方案

- 直接用 `package.json` 的 version 当真值：被否决，因为它是 npm 包元数据，格式受 semver 约束，装不下 YYMMDD.HHMM 与数据规范版本。
- 用一个 `version.json` 同时装两类版本：被否决，两类版本递增时机完全不同，合在一起必然出现「改了一类另一类被迫改动」。
