# ADR-0003 比赛模式的数据模型：房间状态放内存，赛果落库

- 日期：2026-11-08
- 状态：已采纳
- 影响的版本：产物版本 3.1.x（向后兼容的新功能）/ `CONTRACT_VERSION` 由 v2 → **v3**

## 背景

比赛模式需要「同一站点同时承载多个房间、每人每 1.2 秒上报一次进度」。如果把进度写进数据库，一个 8 人房就是每秒 6.7 次写，10 个房间就是每秒 67 次，会把整个站点的读写拖慢——而比赛进度是**瞬时数据**，过期即无用。

## 决策

1. **进行中的房间状态只放进程内存**（`roomRegistry: Map<code, room>`）：状态机、参与者、进度、准备、倒计时、正文快照都在内存，读写微秒级。
2. **数据库只当档案**：建房时插一行 `races`，结束/取消时回写结果与每人名次（`race_participants`）；正常一场比赛全程只写 2~3 次。
3. **开赛瞬间把正文快照进 `races.content_snapshot`**：比赛中文章被编辑/下线/删除都不影响公平性，服务端重启后也能对账。
4. **游客不落库**：游客身份是房间内短期 JWT（`guestId`），房间销毁即失效；`race_participants` 里用 `guest_id` 记录，成绩进 `scores` 标 `source='race_guest'`。
5. **观战席不落库**：观战名额与开关只在内存（`room.spectators`、`room.allowSpectator`），不需要结构变更。

## 后果

- 好的：容量从「每 1.2 秒 N 次写库」降到「每场 2~3 次」，20 房间 / 100 并发玩家的估算成立。
- 好的：赛果、名次、速度都能复查（服务端计时算速度，不采信客户端）。
- 坏的：**只能单进程部署**——房间状态在内存，多进程会各存一份，玩家轮询打到别的进程就是「房间不存在」。已写入 `AGENTS.md` §7 红线（限进程数，不限线程与房间数）。
- 坏的：服务端重启会中断进行中的比赛 → 启动时把库里 `racing/countdown` 的行标为 `aborted`，宁可明确失败也不假装还在跑。

## 被否决的方案

- **进度写库**：写放大不可接受，且进度本身没有长期价值。
- **引入 Redis / socket.io 做多进程与推送**：白名单外依赖，局域网单机场景不需要。
- **观战与开关落库**：观战是一次性状态，落库只会带来迁移成本。
