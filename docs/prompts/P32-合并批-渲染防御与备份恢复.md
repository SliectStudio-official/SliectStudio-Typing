# A 部分：比赛页渲染防御

## A0. 背景：我复现不出来，所以按「绝不允许半成品页面」来做

我在隔离副本 + 无头 Chrome 里试了两种恢复路径：

| 场景 | 结果 |
| --- | --- |
| 比赛中页面重载后自动恢复 | 打字区正常，**272 个字符**、高度 496px、**0 个 JS 错误** |
| 对手先完赛后我方重进 | 打字区正常、排名正确、**0 个错误** |

也就是说**不是必现**。但用户截图里的症状很明显：文章卡、当前排名、我的进度都画出来了，**打字区整个没生成**，页面停在半成品。

我读代码看到两个结构性隐患：

1. `render()` **没有 try/catch**——渲染中途抛一次异常，DOM 就停在抛异常的那一句之前，留下半成品；
2. `tick()` 的 `.catch` 会把这个渲染异常**当成网络错误**吞掉，只累加 `state.tickFailures`，3 次之后才显示「连接中断」，用户在屏幕上什么也看不到。

所以本批的目标不是「修某个已知 bug」，而是：**任何异常都不许留下半成品页面，并且必须能自愈**。

## A1. 要求

| # | 要求 |
| --- | --- |
| A1 | `render()` 整体包 `try/catch`：捕获后 `console.error('[比赛] 渲染异常', e)`（带 `stack`），并置 `state.renderBroken = true`，**本次渲染的 DOM 改动保留但下一次 tick 强制全量重绘** |
| A2 | **自愈重挂**：当 `snap.race.status === 'racing'` 且（`#race-typing` 里 `.char` 数量为 0 **或** `state.engine` 为 null）时，自动 `state.needContent = true` 并**重建引擎**（先 `state.engine = null` 再走 `mountEngine`），不要求用户刷新 |
| A3 | 引擎重建前必须把 `#race-typing` 清空重建（避免残留半截 DOM）；重建后用 `snap.me.progress` 走 `engine.restore()` 恢复已打进度 |
| A4 | 半成品兜底：若连续 **2 次** tick 后打字区仍为空，在打字区位置显示一行提示 + 一个「**重新载入本局**」按钮（`location.reload()`），不要留白 |
| A5 | `tick()` 的 `.catch` 要区分「网络错误」与「渲染异常」：渲染异常**不计入** `tickFailures`，也不触发「连接中断」横幅（避免误报） |
| A6 | 监听 `resize`（节流 200ms）与 `visualViewport` 变化后**重算一次布局**（把 `#view-race` 的断点类重新算一遍），避免窗口尺寸变化后卡在窄屏单列布局里 |
| A7 | 比赛页任何未捕获异常都要能定位：在 `window.addEventListener('error')` 与 `unhandledrejection` 里各打一行 `console.error('[比赛] 未捕获', ...)`，只在 `race.html` 生效 |

## 1. 后端

### 1.1 备份内容（默认口径，已拍板）

| 项 | 是否进包 | 说明 |

### 1.2 端点

| 方法 路径 | 鉴权 | 行为 |
| --- | --- | --- |
| `POST /api/admin/backup/create` | admin | 参数 `{ includeDbConfig?:bool, includeAvatars?:bool }`。流程：`db.backup()` 快照到 `tmp/` → 组装 staging 目录 → `Compress-Archive` 成 `backups/backup-YYYYMMDD-HHMMSS-<VERSION>.zip` → 清理 staging → 返回该备份的元数据（名字/大小/时间/版本/含配置） |
| `GET /api/admin/backup/list` | admin | 列出 `backups/*.zip`（按时间倒序）：名字、大小、创建时间、从文件名解析的版本号；额外返回 `pendingRestore`（是否存在待恢复文件） |
| `GET /api/admin/backup/download/:name` | admin | 下载单个 zip。**文件名必须匹配** `^backup-[0-9]{8}-[0-9]{6}-[0-9.]+(\.zip)$`，否则 400；用 `res.download` 绝对路径 |
| `DELETE /api/admin/backup/:name` | admin | 删除单个 zip；同样做文件名白名单校验 |
| `POST /api/admin/backup/restore` | admin | `multipart/form-data` 上传 zip（上限 **100 MB**，multer 已装）。流程见 §1.3 |
| `POST /api/admin/backup/restore/cancel` | admin | 取消已排队的恢复（删除 `data/typing.db.import` 与 `data/restore-pending.json`） |

### 1.3 恢复流程（关键：不能热替换）

| # | 步骤 | 失败时 |
| --- | --- | --- |
| R1 | 收到 zip → 解压到 `tmp/restore-<时间戳>/` → 读 `manifest.json`；**没有 manifest 或不是本系统的备份 → 400「不是本系统的备份文件」** | 清 tmp，返回 400 |
| R2 | 校验 `typing.db` 的 sha256 与 manifest 一致；打开快照确认 `schema_version` 存在 | 不一致 → 400「备份文件已损坏」 |
| R3 | **强制先自动备份当前库**：调与 `create` 同一段代码生成 `backups/backup-<时间>-pre-restore.zip`（失败则**中止恢复**，不许跳过） | 中止并报「恢复前备份失败」 |
| R4 | 把快照库写到 `data/typing.db.import`；写 `data/restore-pending.json`（内含来源文件名、时间、版本） | 失败 → 清标记 |
| R5 | 返回 `{ success:true, needRestart:true, message:'恢复已排队，重启服务后生效' }` | — |
| R6 | **启动时**（`initDatabase` 之前）检测 `restore-pending.json`：把现库三件套改名为 `typing.db.pre-restore-<时间>` / 对应 `-wal` `-shm`，再把 `typing.db.import` 改名为 `typing.db`，删除 pending 标记，打日志 `[恢复] 已应用 <文件名>` | 任一步失败：保持现库不动，打错误日志并以**现库**继续启动（不能让站点起不来） |

> R6 的顺序必须是「先备份现库文件名 → 再换上新库」，且**换库前必须确认 import 文件大小 > 0**。

## 5. 停止点

- 若 `db.backup()` 在你的 Node/ABI 上不可用（我这边实测可用）→ **停**，报错误原文；
- 若 `Compress-Archive` 因文件被占用而失败（例如直接压 `data/typing.db`）→ **停**，确认你是否换成先快照再压（**本提示词要求先快照**，不许直接压活动库）；
- 若你判断「恢复必须在**没有请求进来**的时候做」需要停机脚本 → **停**，先报方案，别自己加大机制；
- 若发现 `backups/` 会被打进发布包 → **停**，先修打包脚本再谈面板。
