# P33-管理端备份与恢复

> 读的提示词就是本文件。开工时算本文件 sha256，写进执行报告第一行。
> 你是执行方 AI。用户原话：「**管理页面加一个备份网站配置的功能吧 给数据库 配置文件这些备份成 zip 并且支持导入备份文件 还可以对备份文件进行管理**」
> 契约边界：**这不是自更新**（§7 只禁止「给管理面板加升级/自更新能力」）。本批只做**本站自身数据与配置的备份/恢复**，**不下载、不安装、不替换程序代码**。

## 0. 四问（先自己核一遍，不一致就停下报）

| 问 | 答 |
| --- | --- |
| 怎么分类 | 运维类功能。新增管理面板「备份与恢复」+ 端点组 `/api/admin/backup/*` + 存储目录 `backups/`。**不改任何表结构**（`CONTRACT_VERSION` 保持 `v3`），**不新增依赖** |
| 怎么设计 | 数据库用 better-sqlite3 自带的一致性快照 `db.backup()`（我实测：返回 Promise，快照可直接只读打开，`schema_version=v3`）；ZIP 用 PowerShell `Compress-Archive`（与 `make-release.mjs` 同一路子，已验证）；恢复因为 SQLite 文件被进程占用**不能热替换**，改成「排队 + 重启生效」 |
| 怎么做 | 见 §1–§2 |
| 是否有真实参考 | `db.backup()` 来自 better-sqlite3 官方 API（本机实测可用）；ZIP 复用项目内 `make-release.mjs` 的 `Compress-Archive` 写法；**不引第三方** |

## 1. 后端

### 1.1 备份内容（默认口径，已拍板）

| 项 | 是否进包 | 说明 |
| --- | --- | --- |
| `data/typing.db` | **必含** | 用 `db.backup(临时文件)` 做的**一致性快照**，不是直接拷文件（WAL 模式下直接拷会丢数据） |
| `VERSION` / `CONTRACT_VERSION` / `version.json` | **必含** | 备份时如实记下版本，恢复时据此判断兼容 |
| `manifest.json` | **必含** | 备份元信息：`createdAt`、`appVersion`、`contractVersion`、`dbSchemaVersion`、`dbBytes`、`counts`（users/articles/scores 行数）、`includesDbConfig`、`sha256`（对 `typing.db`） |
| `db-config.json` | **默认不含** | 内含 MySQL 明文密码。面板上给一个复选框「同时备份数据库配置（含密码，风险自担）」，**默认不勾** |
| `public/avatars/*` | **默认不含** | 用户上传的头像；同样用复选框「包含用户头像」，默认不勾 |
| `backups/` 自身、`node_modules/`、`tmp/` | **永不含** | 必须显式排除 |

### 1.2 端点

| 方法 路径 | 鉴权 | 行为 |
| --- | --- | --- |
| `POST /api/admin/backup/create` | admin | 参数 `{ includeDbConfig?:bool, includeAvatars?:bool }`。流程：`db.backup()` 快照到 `tmp/` → 组装 staging 目录 → `Compress-Archive` 成 `backups/backup-YYYYMMDD-HHMMSS-<VERSION>.zip` → 清理 staging → 返回该备份的元数据（名字/大小/时间/版本/含配置） |
| `GET /api/admin/backup/list` | admin | 列出 `backups/*.zip`（按时间倒序）：名字、大小、创建时间、从文件名解析的版本号；额外返回 `pendingRestore`（是否存在待恢复文件） |
| `GET /api/admin/backup/download/:name` | admin | 下载单个 zip。**文件名必须匹配** `^backup-[0-9]{8}-[0-9]{6}-[0-9.]+(\.zip)$`，否则 400；用 `res.download` 绝对路径 |
| `DELETE /api/admin/backup/:name` | admin | 删除单个 zip；同样做文件名白名单校验 |
| `POST /api/admin/backup/restore` | admin | `multipart/form-data` 上传 zip（上限 **100 MB**，multer 已装）。流程见 §1.3 |
| `POST /api/admin/backup/restore/cancel` | admin | 取消已排队的恢复（删除 `data/typing.db.import` 与 `data/restore-pending.json`） |

### 1.3 恢复流程（关键：不能热替换）

| # | 步骤 | 失败时 |
| --- | --- | --- |
| R1 | 收到 zip → 解压到 `tmp/restore-<时间戳>/` → 读 `manifest.json`；**没有 manifest 或不是本系统的备份 → 400「不是本系统的备份文件」** | 清 tmp，返回 400 |
| R2 | 校验 `typing.db` 的 sha256 与 manifest 一致；打开快照确认 `schema_version` 存在 | 不一致 → 400「备份文件已损坏」 |
| R3 | **强制先自动备份当前库**：调与 `create` 同一段代码生成 `backups/backup-<时间>-pre-restore.zip`（失败则**中止恢复**，不许跳过） | 中止并报「恢复前备份失败」 |
| R4 | 把快照库写到 `data/typing.db.import`；写 `data/restore-pending.json`（内含来源文件名、时间、版本） | 失败 → 清标记 |
| R5 | 返回 `{ success:true, needRestart:true, message:'恢复已排队，重启服务后生效' }` | — |
| R6 | **启动时**（`initDatabase` 之前）检测 `restore-pending.json`：把现库三件套改名为 `typing.db.pre-restore-<时间>` / 对应 `-wal` `-shm`，再把 `typing.db.import` 改名为 `typing.db`，删除 pending 标记，打日志 `[恢复] 已应用 <文件名>` | 任一步失败：保持现库不动，打错误日志并以**现库**继续启动（不能让站点起不来） |

> R6 的顺序必须是「先备份现库文件名 → 再换上新库」，且**换库前必须确认 import 文件大小 > 0**。

### 1.4 通用要求

| # | 要求 |
| --- | --- |
| G1 | 所有端点仅 admin；非 admin **403**，未登录 **401**（三个分支都要实测） |
| G2 | **保留策略**：`backups/` 里最多留 **10 份**普通备份（`pre-restore` 的也算在内），超出时自动删最旧的；删除前打日志 |
| G3 | 并发保护：同一时刻只允许一个备份/恢复任务（模块级布尔 + 409「已有备份任务在进行」） |
| G4 | 所有临时产物落 `tmp/`，无论成功失败都要清理（`try/finally`） |
| G5 | `backups/` 目录**必须**加进 `.gitignore`，且**不得**被 `make-release.mjs` 打进发布包（`DENY` 里已有 `releases/`，请确认 `backups/` 不会被 `public/` 白名单带进去——它在根目录，本身就不在打包白名单里，报告里确认一次即可） |
| G6 | 凭据不进日志：`db-config.json` 只记「是否包含」，**不许**把内容或密码写进日志/响应 |
| G7 | 生成 zip 用 `execFile` 调 PowerShell，写明超时（120 秒）与失败判据；不用 `shell: true` |

## 3. 验收（逐条贴读数）

| # | 场景 | 判据 |
| --- | --- | --- |
| 1 | 鉴权 | 未登录 **401**、普通用户 **403**、admin **200**（备份三个端点各贴一条） |
| 2 | 创建备份 | 点「开始备份」→ 返回 `{name, bytes, createdAt, appVersion, includesDbConfig:false}`；`backups/` 下出现文件；zip 内条目贴清单（应含 `typing.db`、`VERSION`、`CONTRACT_VERSION`、`version.json`、`manifest.json`，**不含** `db-config.json`） |
| 3 | 一致性 | 解出 `typing.db` 用只读连接打开：`schema_version=v3`；`manifest.counts` 与库内实际行数一致（贴三个数字对照） |
| 4 | 可选内容 | 勾选「含数据库配置」再备份：zip 内出现 `db-config.json`，`manifest.includesDbConfig=true`；**默认不勾时不得出现** |
| 5 | 列表与下载 | `list` 返回该项；下载 HTTP **200** 且 `Content-Disposition` 带文件名；下载一个恶意名 `../db-config.json` → **400** |
| 6 | 删除 | 删除后 `list` 里消失、文件不存在；再删同一个 → **404** |
| 7 | 恢复：校验 | 上传一个无关 zip → **400「不是本系统的备份文件」**；上传被改坏 byte 的备份 → **400「备份文件已损坏」** |
| 8 | 恢复：排队 | 上传合法备份 → `{needRestart:true}`；`data/restore-pending.json` 存在、`data/typing.db.import` 大小 > 0；`backups/` 里多出一份 `pre-restore` 备份 |
| 9 | 恢复：重启生效 | 重启服务：日志出现 `[恢复] 已应用 …`；`data/typing.db` 大小变化、`typing.db.pre-restore-<时间>` 存在；`/api/version` 正常、能登录（贴读数） |
| 10 | 恢复：可取消 | 排队后点「取消恢复」→ 两个标记文件消失、`list.pendingRestore=false`；重启后仍是原库 |
| 11 | 保留策略 | 连续生成 12 份（可临时把上限改成 3 验证）：只剩最新 N 份，最旧的被删（贴 `list` 长度） |
| 12 | 并发保护 | 同时点两次备份 → 第二次 **409**（贴两条响应） |
| 13 | 面板交互 | 420px 下变卡片式；恢复横幅在刷新后仍在；删除有二次确认（贴三张截图路径） |
| 14 | 回归 | 现有 12 个面板都还能打开；练习/比赛/个人中心不受影响；`make-release.mjs` 打的包**不含** `backups/` 与 `tmp/`（贴打包输出里的审计行） |

## 5. 停止点

- 若 `db.backup()` 在你的 Node/ABI 上不可用（我这边实测可用）→ **停**，报错误原文；
- 若 `Compress-Archive` 因文件被占用而失败（例如直接压 `data/typing.db`）→ **停**，确认你是否换成先快照再压（**本提示词要求先快照**，不许直接压活动库）；
- 若你判断「恢复必须在**没有请求进来**的时候做」需要停机脚本 → **停**，先报方案，别自己加大机制；
- 若发现 `backups/` 会被打进发布包 → **停**，先修打包脚本再谈面板。
