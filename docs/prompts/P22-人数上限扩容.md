# P22-房间人数上限扩到 100（含性能护栏）

> 读的提示词就是本文件。开工时算本文件 sha256，写进执行报告第一行。
> 你是执行方 AI。用户要求：**房间人数上限从最高 8 人扩到最多 100 人**。
> 依据 `docs/设计四问模板.md`，四问已答完（§0.1）。**不能只改一个数字**：8 → 100 会连带出容量、带宽、渲染三类问题，§2 的护栏是同批必做项。

## 0. 用户原话与现状

| 项 | 现状 |
| --- | --- |
| 前端 | `race.html` 的 `#create-max` 只有 2 / 4 / 6 / 8 四个选项 |
| 后端 | `server.js:1026` `if (!Number.isInteger(mp) || mp < 2 || mp > 8)` → 400「房间人数上限必须在 2 到 8 之间」 |
| 观战席 | `spectatorCap(maxPlayers) = max(1, floor(maxPlayers × 0.1))` → 8 人房 1 席；**100 人房自然是 10 席** |
| 轮询 | 客户端固定 `setInterval(tick, 1200)`；**快照每次 tick 都带文章全文 `content`** |
| 渲染 | 排名列表与选手列表**不截断**，全量渲染 |

## 0.1 四问（已答）

| 问 | 答 |
| --- | --- |
| 分类 | 前后端 + 容量参数变更；**不改表结构**（`max_players` 字段已是 INT）；但会新增一个 `settings` 键（§2.4），不改表结构 |
| 设计 | 上限 2–100；观战席沿用 10% 公式（100 人房 → 10 席）；三类护栏：快照瘦身、轮询退避、渲染截断 |
| 怎么做 | 见 §1–§3；验收用脚本造 100 个游客参赛，读响应字节数、轮询间隔、渲染行数 |
| 参考 | 无外部原文可引（搜索不可用）。依据通用工程判断：轮询型多人同步必须把"快照体积 × 频率 × 人数"当预算算。**本项目自定** |

## 1. A 组：上限与校验（`server.js` + `race.html` + `race.js`）

| # | 要求 |
| --- | --- |
| A1 | 后端校验改为 **2 ≤ maxPlayers ≤ 100**，文案「房间人数上限必须在 2 到 100 之间」；非整数/缺省按 8 处理（缺省值不变） |
| A2 | 前端 `#create-max` 从下拉改为**数字输入 + 快捷按钮组**（2 / 4 / 8 / 16 / 32 / 64 / 100），输入框 `type="number" min="2" max="100" step="1"`；非法值即时提示并不允许提交 |
| A3 | 快速匹配房仍固定 `maxPlayers=2`，不受影响 |
| A4 | 观战席容量**不改公式**：`spectatorCap = max(1, floor(maxPlayers × 0.1))`（100 人 → 10 席、50 → 5、20 → 2、8 → 1）；建房回执与快照里的 `maxSpectators`/`spectatorSeats` 随之变 |
| A5 | 大厅房间列表的「x/y 人」与「观战 n/N」自动显示新数值，不需要特别处理，但要验证 100 人房的显示不被截断 |

## 2. B 组：性能护栏（同批必做）

### 2.1 快照瘦身：正文只发一次

```
现状：每次 tick 响应都含 race.content（281 字的文章全文）+ players[] + spectators[]
100 人房 → 每次 ~15–25KB × 83 次/秒 ≈ 1.4–2MB/s，只为一个房间
```

| # | 要求 |
| --- | --- |
| B1 | `/api/race/tick` 默认**不下发** `race.content`，只给 `charCount` / `articleTitle` |
| B2 | 客户端首次进入房间与刷新恢复时，在 tick 请求体里带 `wantContent: true`；服务端仅在该请求（以及 `status` 首次变为 `racing` 的那一次）返回 `content` |
| B3 | 客户端缓存 `content`（内存即可），后续 tick 没有 `content` 时沿用缓存；**没有缓存且需要打字 → 用 `wantContent` 再要一次**，不许渲染空文本 |
| B4 | 目标：**100 人房单次 tick 响应（不含 content）≤ 6KB**（在报告里贴实测字节数） |
| B5 | `spectators` 列表在人数 > 20 时**只返回前 20 + 自己**，并附 `spectatorTotal`；`players` 列表**不截断**（比赛必须全员可见），但要在报告里给出 100 人时 players[] 的字节占比 |

### 2.2 轮询退避

| # | 要求 |
| --- | --- |
| B6 | 客户端轮询间隔按房间人数自适应：**≤8 人 1200ms**、**9–32 人 2000ms**、**>32 人 3000ms** |
| B7 | 例外：`countdown` 阶段与 `racing` 中"自己还在打字"时保持 **1200ms**（保证倒计时与名次跳变的观感） |
| B8 | 间隔切换不得导致漏帧或重复 tick：保证任意时刻只有一个 tick 在飞（既有的 in-flight 保护沿用） |
| B9 | 观战者同样适用（>32 人 3000ms） |

### 2.3 渲染截断

| # | 要求 |
| --- | --- |
| B10 | 比赛中的排名列表（`#race-rank`）只渲染 **前 20 名 + 自己 + 房主**，其余折叠为一行「还有 N 人」，点开才渲染全部（点开后按需渲染，不做虚拟滚动） |
| B11 | 等待厅选手列表容器设 `max-height: 40vh; overflow-y: auto`，滚动条走 P21 G 组那套令牌样式 |
| B12 | 100 人房页面不得出现横向溢出（`scrollWidth <= clientWidth`），420px 同样 |

### 2.4 总席位护栏（防把机器压垮）

| # | 要求 |
| --- | --- |
| B13 | 新增 `settings` 键 `race_max_total_players`，**默认 200**；建房时校验"当前所有活动房间的 maxPlayers 之和 + 新房 maxPlayers ≤ 该值"，超出返回 400「当前总席位已满（已用 x / 上限 y），请稍后再建房」 |
| B14 | 管理面板的「比赛房间」区块加一个只读统计：**当前活动房间总席位 x / 上限 y**（不要求可编辑，若要可编辑放同一行的数字框，1–500） |
| B15 | 只加 key/value 行，不改表结构；不改 `CONTRACT_VERSION` |

## 5. 停止点

- 若 100 人房 tick 响应（不含 content）无法压到 6KB → 停，报 players[] 的字段占用，讨论是否裁剪字段（例如去掉 `lastSeen`、`ip`）；
- 若轮询退避导致"名次跳变太慢"影响比赛公平 → 停，先报方案（可考虑 >32 人时提高退避上限但保留 1200ms 于最后 10 秒）；
- 若 `race_max_total_players` 与 `race_max_rooms` 语义冲突（例如房间数未满但总席位满）→ 按本提示词 B13 为准，并在报告里说明。
