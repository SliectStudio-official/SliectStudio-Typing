# P26-匹配入口与房间生命周期收口

> 读的提示词就是本文件。开工时算本文件 sha256，写进执行报告第一行。
> 你是执行方 AI。用户在真机上发现三个问题，本批一次修完。**P25.2（引导页动画）在跑，别碰它的文件**：本批只动 `server.js`、`public/nav.js`、`public/home.js`、`public/race.js`、`public/race.html`、`public/admin.js/html`、`public/style.css` 里与本批相关的极小片段。

## 0. 用户原话与我的定位

> 「如果一边开始匹配，跟另一台设备匹配成功的话，后面匹配的设备才会进比赛，前一台设备会一直显示在匹配，但是这个时候其实已经在比赛了，而且前一台设备还可以单方面解散比赛，匹配只有退出没有解散，另外给每一场匹配跟房间加一个最长时长防止过度消耗资源，匹配的房间最高 1 小时留存，比赛房间可以调整，最高三小时。」

| # | 现象 | 我查到的根因 |
| --- | --- | --- |
| 1 | 两台设备都点匹配，只有**后点的那台**进了比赛；先点的那台一直停在"匹配中" | 引导页 `home.js` 只在**页面加载时**查一次 `/api/race/match/status`（`initMatch()` 由启动调用一次），**没有周期轮询**；而引导页**不加载 `nav.js`**，`nav.js` 的 1 秒轮询不会跑。所以先点的设备永远不知道已经配对成功 |
| 2 | 先点那台还能**单方面解散**这场比赛 | 匹配房创建时 `matchmade: true`，但**解散三端点没有检查这个字段**，`buildSnapshot` 也把它当成普通房 → 房主看到「解散房间」/「发起解散投票」。匹配房本质是系统自动生成的对局，**只应该有"退出比赛"** |
| 3 | 房间没有总时长上限，可能长期占资源 | `cleanupRooms()` 只有三条结束条件：全员离线（60/30/120s）、房主 5 分钟离线、`racing` 时 `charCount×2` 分钟。**`waiting`/`countdown` 状态没有任何总时长上限** |

## 1. A 件：匹配成功后**两台设备都必须进比赛**

| # | 要求 |
| --- | --- |
| A1 | `public/home.js`：进入匹配态后**每 1.5 秒**轮询一次 `/api/race/match/status`；收到 `status === "matched"` 且带 `code` → 立刻 `location.href = "race.html?code=" + code` |
| A2 | 页面从后台切回前台（`visibilitychange` → 可见）与窗口获得焦点（`focus`）时**立即补查一次**，不等下一个 1.5 秒 |
| A3 | 轮询失败不得把卡片复位成 idle（网络抖动很正常）；只有服务端明确返回 `status === "idle"` 才复位 |
| A4 | 引导页离开（`beforeunload`）或取消匹配时清掉定时器，避免多个循环叠加 |
| A5 | `nav.js` 的匹配条轮询保持现状（1 秒），但**跳过已在比赛页的情况**，避免比赛页里再跳转 |
| A6 | 服务端 `/api/race/match/status` 与 `/join` 的 `matched` 返回必须**幂等**：同一用户在同一房间里多次请求都返回同一个 `code`（现有 `findRoomByUser` 已满足，验收里要证明） |
| A7 | 匹配成功后，双方客户端的 `raceMatchPending` 标记都要清掉，避免下次进首页误判仍在排队 |

## 2. B 件：匹配房**只有退出，没有解散**

| # | 要求 |
| --- | --- |
| B1 | 服务端：`POST /api/race/dissolve/start`、`/vote`、`/cancel` 三个端点，命中 `room.matchmade === true` 时一律 **400**，文案「匹配对局不支持解散，只能退出」 |
| B2 | 快照里 `race.matchmade` 必须下发（现在没暴露），前端据此决定显不显示解散入口 |
| B3 | 前端 `race.js`：`matchmade === true` 时**不渲染**「解散房间」与「发起解散投票」两个按钮（DOM 里根本不出现，不是隐藏）；顶部按钮文案为「退出比赛」（比赛中为「退出比赛」，确认文案说明**视为放弃本局**） |
| B4 | 匹配房一方退出 → **对手直接判胜**：房间结束、`cancelledReason` 用新值 `opponent_left`，留下的一方看到「对手已退出，你获胜」并可正常回大厅（成绩按已完赛/未完赛规则处理，未打完不计名次） |
| B5 | 退出方看到「已退出本局」，不得看到"房间已解散" |
| B6 | 手动房（`matchmade !== true`）行为完全不变：房主等待态仍是「解散房间」、≥3 人走解散投票 |

## 3. C 件：房间总时长上限

| # | 要求 |
| --- | --- |
| C1 | **匹配房**：从 `createdAt` 起最多 **60 分钟**，到点强制结束（`cancelledReason = "duration_limit"`），不可由房主延长 |
| C2 | **手动房**：建房时可选时长 **30 / 60 / 120 / 180 分钟**（默认 60），服务端写入 `room.maxDurationMs`；**上限由设置项 `race_max_duration_minutes` 控制，默认 180，范围 1–180**，超过上限的请求 → 400「房间最长时长不能超过 180 分钟」 |
| C3 | `cleanupRooms()` 增加统一判定：`now - room.createdAt > room.maxDurationMs` → `waiting`/`countdown` 用 `cancelRoom(room, "duration_limit")`；`racing` 用 `finalizeRoom(room, "time_limit")`（沿用既有超时结算路径，保留已完赛成绩） |
| C4 | 判定顺序：**先离线（P21 B）再时长**，避免把"人还在但超时"和"人都走了"混成一条 |
| C5 | 房间列表 `/api/race/list` 与快照增加剩余时间字段（`remainMs` 或 `expiresAt`），前端在房间行/等待厅显示「剩余 42 分钟」，最后 5 分钟变警示色 |
| C6 | 管理面板「比赛房间」区块增加 `race_max_duration_minutes`（1–180，默认 180）输入与说明 |
| C7 | 结束原因文案补两条：`duration_limit` →「房间到达最长时长，已结束」；`opponent_left` →「对手已退出，本局结束」（`race.js` 的 `CANCELLED_TEXT` 映射里加） |
| C8 | 匹配队列条目本身的过期清理保持现状（5 分钟 stale） |

## 3.5 F 件：匹配卡「取消 ×」未居中（用户实测）

用户截图里 × 明显偏下、且与计时段不在同一水平线。我核到原因：`#view-dashboard .dash-match-close` 写的是

```css
position: absolute; right: 8px; top: calc(50% - 10px); transform: translateY(-50%);
```

`calc(50% - 10px)` 已经上移 10px，再叠加 `translateY(-50%)`，实际视觉中心比几何中心**偏上 10px**；而横向的 `align-items/justify-content: center` 是对的。

| # | 要求 |
| --- | --- |
| F1 | 改为 `top: 50%; transform: translateY(-50%)`（去掉 `-10px`），或直接用 `inset-block: 0; margin: auto`；横向保持 `justify-content: center` |
| F2 | 验收口径：× 图标的包围盒中心与卡片垂直中线偏差 **≤1px**；与左侧计时文字的中线偏差 ≤2px |
| F3 | 点击区仍为 32×32（P25.3 已定），不得为了对齐而放大 |

## 6. 停止点

- 若要"匹配房一方退出即判胜"必须改结算协议（`scores` 写入或名次规则）→ **停**，先报方案；本批只允许改房间状态与文案；
- 若"两队都进比赛"需要把匹配改成 WebSocket/SSE → **停**：本批只用轮询解决；
- 若建房时长要支持"任意分钟数"（不是 30/60/120/180 四档）→ **停**，先问用户；
- 若 `maxDurationMs` 与 P21 B 的离线阈值出现语义冲突（例如房间因离线结束，但时长也刚好到）→ 按 C4 的"先离线后时长"实现，并在报告说明；
- 若需要给引导页加"剩余时间"显示 → **不要在 P26 做**（P25.2 正在改引导页），记一行待办即可。
