## 2. 逐项交付（三组提交，各自可独立回滚）

### A 组：K-05 鉴权只信 payload，不复核数据库

- 位置：`server.js` 第 176-188 行 `authMiddleware`。
- 现状：`jwt.verify` 后直接 `req.user = decoded`，于是降级、删号、改密都不影响既有 token（7 天有效）。
- 改法：
  1. 保持原有的头解析与 `verify` 失败分支（401 文案不变）。
  2. verify 成功后只取 `decoded.id`，回查一次：`SELECT id, username, role FROM users WHERE id = ?`。
  3. 查不到行 → 401 `{ error: '用户不存在或登录已失效' }`。
  4. 查到行 → `req.user = { id: row.id, username: row.username, role: row.role }`，**以库里的 role 为准**，payload 里的 `role` / `username` 一律不采信。
  5. 不加缓存、不加 token 版本号、不动 `adminMiddleware`、不改 token 有效期（仍 7 天）。
- 已知残留（必须写进报告的不确定项）：**改密码后旧 token 依然有效**，因为本批没有失效机制。这条登记在坑库 K-05 的残留风险里，属后续批次。
- 验收口径：

| 步骤 | 期望 |
| --- | --- |
| 用 `__verify_` 用户登录拿到 token A，由管理员把它提成 admin，再登录拿到 token B，然后降回 user | 200 |
| 用 token B 访问 `GET /api/admin/users` | **403**（不再因为 payload 里写着 admin 而放行） |
| 用 token B 访问 `GET /api/auth/me` | 200，`role` 为 `user` |
| 删除该用户后，用 token B 再访问 `GET /api/auth/me` | **401**（用户不存在） |
| 改密码后用旧 token 访问任意登录端点 | 仍 200 —— 这是本批已知残留，如实记录 |
| 中文用户名、昵称含空格的老账号登录后访问 `/api/user/profile` | 正常，无 401 |

### B 组：K-06 非生产分支落回硬编码密钥

- 位置：`server.js` 第 17-24 行（`isProduction` 与 `JWT_SECRET`）与第 1672 行附近的启动段。
- 现状：无 `JWT_SECRET` 环境变量时落回硬编码字符串，任何人读源码即可伪造 admin token。
- 改法：
  1. 删除硬编码常量与 `isProduction && !JWT_SECRET` 抛错分支；`isProduction` 若不再被其它地方引用则一并删除（避免留下未使用变量）。
  2. 把 `JWT_SECRET` 从 `const` 改为模块级 `let`，在 `initDatabase()` 末尾调用新增的 `loadOrCreateJwtSecret()` 赋值。
  3. 取值顺序：`process.env.JWT_SECRET` 优先 → 其次读 `data/jwt-secret.txt` → 都没有则用 `crypto.randomBytes(32).toString('hex')` 生成并写入该文件（`data/` 目录已存在；写入失败则报错退出，不要静默降级）。
  4. 启动日志打一行来源，**绝不打印密钥内容**：环境变量 / `data/jwt-secret.txt`（本次新建）。
  5. `jwt.sign` / `jwt.verify` 的调用点保持不变（仍用变量名 `JWT_SECRET`）。
- 验收口径：

| 步骤 | 期望 |
| --- | --- |
| 删掉 `data/jwt-secret.txt`，不设 `JWT_SECRET` 启动 | 启动成功，文件被创建，日志显示来源为新建；内容为 64 位十六进制 |
| 用该实例登录拿 token，重启服务再用同一 token 访问 `/api/auth/me` | 200（密钥被复用，没有被重新生成） |
| 设 `JWT_SECRET` 环境变量启动 | 日志显示来源为环境变量；此时用不设环境变量实例签发的 token 访问 → 401 |
| 全仓库检索硬编码串 | `typing-practice-jwt-secret-key-2026` 在 `server.js` 中已不存在 |
| 日志与报告里检索 | 不含密钥全文 |

### C 组：K-07 最后管理员与初始化接口 + 登录限流 + 密码长度

**C1 最后管理员保护**

- 位置：`server.js` 第 367 行 `PUT /api/admin/users/:id`。
- 改法：当 `role === 'user'` 且目标用户当前 `role === 'admin'` 且 `SELECT COUNT(*) FROM users WHERE role='admin'` 为 1 时，返回 400 `{ error: '不能降级唯一的管理员账户' }`。其余校验与更新逻辑不动。

**C2 初始化接口限定本机**

- 位置：`server.js` 第 206 行 `POST /api/bootstrap/create-admin`。
- 改法：进入处理前判 `req.ip` 是否为回环地址（接受 `127.0.0.1`、`::1`、`::ffff:127.0.0.1`），不是则返回 403 `{ error: '首次初始化只允许在服务器本机进行' }`。已有管理员时仍按原逻辑返回 400。`GET /api/bootstrap/status` 保持匿名可读不要动（启动脚本要用）。
- **必须写进报告的副作用**：从局域网其它机器首次打开 `setup.html` 会被 403 拦住，这是拍板后接受的取舍；提示文案要让用户知道去服务器本机完成初始化。

**C3 登录失败限流**

- 位置：`server.js` 第 273 行 `POST /api/auth/login`。
- 改法：模块级 `Map` 记失败次数，键为 `req.ip + '|' + 用户名小写`；窗口 10 分钟、同键 5 次失败后进入锁定，锁定期内的尝试（包括密码正确的）一律返回 429 `{ error: '尝试次数过多，请稍后再试' }`；登录成功即清除该键。Map 条目上限 10000，超出时整体清空并 `console.warn` 记录一次（有界，不无界增长）。过期键在每次访问时惰性清理，不新增定时器。

**C4 密码长度 6 至 72 字节**

- 位置：四处——`POST /api/auth/register`、`PUT /api/auth/me`（`newPassword`）、`PUT /api/user/password`（`newPassword`）、`PUT /api/admin/users/:id`（`password`）。
- 改法：保留原有「至少 6 位」判断，追加 `Buffer.byteLength(pw, 'utf8') > 72` 时返回 400 `{ error: '密码不能超过 72 字节' }`。用字节而不是字符，因为 bcrypt 只取前 72 字节。

- 验收口径：

| 步骤 | 期望 |
| --- | --- |
| 只有一个管理员时，把它降级为 user | 400 `不能降级唯一的管理员账户` |
| 再建一个管理员后，降级其中一个 | 200 |
| 从服务器本机浏览器访问 `setup.html` 对应的 `/api/bootstrap/create-admin` | 已有管理员时 400（不是 403） |
| 从局域网 IP 访问同一接口（用 `http://<局域网IP>:3000` 打开页面后调用） | 403 与「只允许在服务器本机进行」 |
| 连续 5 次错误密码 | 前 5 次 400，第 6 次 **429** |
| 锁定期间用正确密码登录 | 429 |
| 锁定期间用另一个人不存在的用户名尝试 | 400（键是按 ip+用户名，不互相影响） |
| 注册 72 字节密码 | 200 |
| 注册 73 字节密码 | 400 `密码不能超过 72 字节` |
| `admin.html` 修改他人密码为 73 字节 | 400 |
| 回归：P1 的删文章 / 删用户 / 错字记录三条 | 仍 200 |

无凭据端点用命令行；带凭据端点用浏览器 Console（token 从 `localStorage` 取，凭据不进命令行）：

```powershell
node --check server.js
# 限流：连打 6 次错误密码，观察第 6 次是否为 429
1..6 | ForEach-Object { curl.exe -s -o NUL -w "%{http_code} " -X POST http://localhost:3000/api/auth/login -H "Content-Type: application/json" -d "{\"username\":\"rate_probe\",\"password\":\"wrong\"}" }
curl.exe -s -X POST http://localhost:3000/api/auth/login -H "Content-Type: application/json" -d "{\"username\":\"rate_probe\",\"password\":\"wrong\"}"
```

## 3. 数据准备与清理（同前两批约定）

1. 动手前把 `data/typing.db` 备份到 `tmp/typing-backup-<日期时间>.db`，报告写文件名。
2. 测试对象以 `__verify_` 开头；结束后清理并写「已清理，剩余 0 条」。
3. 允许在 `data/` 下新增 / 删除 `jwt-secret.txt`（本批唯一对 `data/` 的豁免），**不得改 `data/typing.db`**、不得手写 SQL 绕过接口。
4. **验收会改动现有管理员的密码或角色**：所有涉及真实账号的操作必须先新建 `__verify_` 账号来做，不许动现有的唯一管理员账号。
5. 验收结束时把 `data/jwt-secret.txt` 恢复成「生产该用的那一份」——若原有部署依赖 `launcher.config.ps1` 的环境变量，则删除该文件，并在报告里写明最终状态。

## 4. 停止点

- 限流把你自己或管理员锁死在门外（重启进程即清空内存计数，但必须先报读数，不要靠调大阈值绕过）
- `setup.html` 在本机也无法完成初始化（先确认 `req.ip` 实际值，报出来再判断）
- `authMiddleware` 加查询后出现明显变慢或数据库忙（报读数，不要加缓存自行优化）
- 任何需要 schema 变更、需要新依赖、需要改前端的情形
- 任一验收与期望不符且原因不明

## 5. 交付格式

四段式加执行报告，写进 `docs/reports/P3-执行报告.md`，第一行写 `docs/prompts/P3-鉴权链.md` 的 sha256。报告必须含：

1. 改了什么：A / B / C 三组分开列，每处写文件路径与那一行的前后对照。
2. 怎么验证：贴 §2 各表实际读数（限流要贴出 6 次的 HTTP 码序列）。
3. 怎么回滚：三组各自改回哪一行；B 组额外写「删除 `data/jwt-secret.txt` 并把密钥逻辑改回常量」。
4. 不确定项：必须包含「改密后旧 token 仍有效」与「局域网无法首次初始化」两条。
5. 数据结构与关系清单：预期「无变化」（没有加列），也要写。
6. 上线提示：一句话写明「部署后所有既有登录态立即失效，用户需重新登录」。
