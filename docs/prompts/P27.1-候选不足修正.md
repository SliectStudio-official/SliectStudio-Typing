# P27.1-修正：候选不足时快速匹配直接不可用（阻塞级）

> 读的提示词就是本文件。开工时算本文件 sha256，写进执行报告第一行。
> 你是执行方 AI。**P27 的抽文逻辑在真实数据库上跑不起来**，本批修掉。

## 0. 我复跑到的证据（阻塞级）

我在生产库副本上按 P27 的流程跑了一次真实匹配：

```text
A join →  {"status":"waiting","waiting":1}
B join →  {"status":"waiting","waiting":2,"hint":"可用候选文章不足三篇，请稍后再试"}   ← 配对根本没发生
A tick →  {}   （没有房间，状态为空）
```

原因很简单——**真实库里 `status=approved` 的文章只有 3 篇**：

```text
已通过文章数: 3    长度分布: 72, 245, 281
200–400 区间: 2 篇    100–800 区间: 2 篇
```

而 P27 要求「三篇互不相同」→ 永远凑不齐 3 篇 → **快速匹配在整个站上完全不可用**（点多少次都停在"正在寻找对手"）。这是我提示词里的设计错误，不是你的实现问题。

## 1. 改成什么样

| # | 要求 |
| --- | --- |
| A1 | 候选数改为 **`min(3, 可选篇数)`**，不再硬性要求 3 篇 |
| A2 | 可选池放宽：**所有 `status=approved` 且正文非空的文章**都算候选；排序时**优先** 200–400 字，其次 100–800，最后其余（稳定排序，保证抽奖观感） |
| A3 | 三种情况分别处理：<br>· 可选 ≥3 → 三卡抽奖（现状不变）<br>· 可选 = 2 → **两张卡**轮转抽奖（动画时长不变，只是少一张卡）<br>· 可选 = 1 → **跳过抽奖**：单卡淡入居中 800ms 后直接进倒计时（`resolution` 记为 `single`） |
| A4 | 可选 = 0（一篇可用文章都没有）时：保持现在的 hint「暂无可用文章，请稍后再试」，**并且不得把用户留在队列里**——即配对前先检查池子，不足就返回 `{status:"waiting", hint:"暂无可用文章"}` 但**不创建房间**（现状已是如此，确认即可） |
| A5 | 服务端日志：候选数 < 3 时打一行 `[匹配] 候选不足 三篇→N 篇`，便于以后排查 |
| A6 | 前端：`#view-reveal` 按 `candidates.length` 渲染 1/2/3 张卡；布局与动画自适应（两张卡时并排居中，一张卡时居中放大）；`prefers-reduced-motion` 逻辑不变 |
| A7 | 快照 `race.reveal` 增加 `resolution` 字段（`three` / `two` / `single`），供前端与验收读取 |

## 2. 验收（逐条贴读数）

| # | 场景 | 判据 |
| --- | --- | --- |
| 1 | **真实库能配对** | 用**生产库副本**（approved 只有 3 篇：72/245/281 字）跑 A/B 匹配：B 的 `/join` 必须返回 **`matched` + code**（不再是 waiting + hint）；贴两台 tick 的 `status` 与 `reveal.candidates` 长度 = **2** |
| 2 | 两卡抽奖 | 上一条房间里贴：两张候选卡 id、轮转高亮的 ≥3 个采样时刻、落点 = `resolvedArticleId` |
| 3 | 单卡场景 | 临时把库里 approved 改成只剩 1 篇（沙箱里改，不动生产）：贴 `reveal.resolution = "single"`、卡片数 1、800ms 后进 `countdown`、无轮转动画 |
| 4 | 空池场景 | 沙箱里把 approved 全下架：`/join` 返回 waiting + 「暂无可用文章」，**不创建房间**（贴 `activeRoomCount()` 前后都是 0） |
| 5 | 三卡回归 | 沙箱里补足 ≥3 篇时，`reveal.candidates` 长度 = 3、动画仍是四段（贴读数） |
| 6 | 同局一致 | 两台设备的 `reveal.resolvedArticleId` 与 `resolution` 完全相同 |
| 7 | 回归 | P26 的两台都跳转、匹配房无解散、P27 的匹配房无观战、H 件按钮原地变形、I 件底栏计时——各贴一条读数 |

## 4. 停止点

- 若为了让三卡抽奖成立而想往生产库插测试文章 → **绝对不行**，这是红线；只能按 A1 的自适用篇数实现；
- 若你判断"库里有 3 篇就不该有这个问题"→ 停，先复跑我上面给的 SQL（`SELECT id,title,length(content) FROM articles WHERE status="approved"`）核对，再决定。
