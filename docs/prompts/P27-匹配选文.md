# P27-匹配成功后系统抽文（简化版：取消玩家选择）

> 读的提示词就是本文件。开工时算本文件 sha256，写进执行报告第一行。
> 你是执行方 AI。前置：**P26 已落地**（匹配成功后所有设备都跳进比赛页）。
> 用户口径（2026-11-08）：「匹配没有观战吧 自建房是手动选文章 不用这个逻辑 这个逻辑只是匹配用」——据此补 §2.5：**匹配房不开放观战**；手动建房永远走自己的选文章流程，不碰 reveal。
> 用户原话三（大厅匹配卡）：「这个时间要在原按钮位置 是原按钮直接变化的 而不是现在这样突然又变上去了」——见 §2.6 H 件。
> 用户原话四（底部指示条）：「下面匹配时间的指示也没了 加回来的同时保留我要求的按钮设计」——见 §2.7 I 件。
> **本版是简化版**：用户原话「既然只有三篇似乎没必要做选择了 直接改成全部系统随机？」——**取消玩家选择**，只保留"三篇里抽一篇"的抽奖动画。

## 0. 流程（一个 `reveal` 阶段，没人做选择）

```text
两台设备点匹配
   ↓ 配对成功（P26 保证两台都跳转）
[reveal] 比赛页显示「匹配成功」+ 三篇候选卡摆在中央
   ↓ 系统抽奖动画（约 1.2s，落点由服务端定死）
中选那篇移到正中放大 → 转场
   ↓
[countdown] 既有 3 秒全屏倒计时
   ↓
[racing] 打字比赛
```

| # | 规则 |
| --- | --- |
| R1 | `reveal` **只用于匹配房**（`matchmade === true`）；手动建房流程不变（房主选文章 → waiting） |
| R2 | 三篇候选：`status=approved`、字数 200–400（不足放宽 100–800）、互不相同；**其中一篇是服务端已经定好的结果**，另两篇只是抽奖道具 |
| R3 | 结果由**服务端**决定（复用现有 `createMatchedRoom` 的随机选文逻辑即可），`reveal` 阶段把 `resolvedArticleId` 一并下发；**前端不得自己随机** |
| R4 | `reveal` 时长 **1500ms**（服务端用 `revealEndsAt` 控制），到点自动进 `countdown`；客户端动画可以稍长/稍短，但**不得改变结果** |
| R5 | 没有玩家输入、没有提交端点、没有超时分支、没有"对方选了什么"——这些全部不要 |
| R6 | 观战者看同一套动画，不可交互 |
| R7 | 房间时长上限（P26 C）对 `reveal` 同样生效 |
| R8 | 抽中文章后回填 `races.article_id`（**不改表结构**） |

## 2.5 G 件：匹配房不开放观战（本次新增）

**代码现状**：`createMatchedRoom` 里写着 `allowSpectator: true` 并调用 `initSpectatorState(room)` —— 也就是说**现在匹配房是开放观战的**（外部凭房间码+密码还能以观战身份进来）。这与你说的"匹配没有观战"不符，本批改掉。

| # | 要求 |
| --- | --- |
| G1 | 服务端：匹配房创建时 `spectatorEnabled = false`、`spectatorSeats = 0`、`maxSpectators = 0` |
| G2 | 服务端：`/api/race/join` 的 `asSpectator` 分支遇到匹配房 → **400**「匹配对局不支持观战」；`/api/race/spectate/{settings,self,assign}` 对匹配房同样 **400**，同一文案 |
| G3 | 服务端：匹配房 `room.spectators` 始终为空；快照 `spectators = []`、`spectatorCount = 0`、`maxSpectators = 0` |
| G4 | 前端 `race.js`：`matchmade === true` 时**不渲染**等待厅右侧观战席面板、不渲染「进入观战席 / 回到选手席」按钮、不渲染比赛页左侧「观战席」只读块（DOM 里不出现，不是隐藏） |
| G5 | 大厅房间列表：匹配房不显示「观战 n/N」（显示「—」或省略该段） |
| G6 | **手动房完全不变**：P20 观战席模型（开关、free/host、席位数、容量公式、导播台、P23 迷你条）全部保留 |

## 2.6 H 件：大厅「快速匹配」按钮要原地变形，不许跳位

代码现状（`public/race.html` 30–44 行）是两套互斥 DOM，而且内部顺序相反：

idle：`#quick-match-idle` = 提示段落 → 按钮；
waiting：`#quick-match-waiting` = 按钮 → 提示段落。

所以切到匹配态时按钮跑到了提示文字上方，整块高度也变了——就是你说的“突然又变上去了”。

| # | 要求 |
| --- | --- |
| H1 | 合并成一套 DOM：一个提示段落 `#quick-match-hint` + 同一个按钮 `#btn-quick-match`（提示在上、按钮在下，与 idle 一致）；`#quick-match-idle` / `#quick-match-waiting` 两套互斥容器删掉，或至少保证只留一套节点且顺序一致 |
| H2 | 匹配态只做原地变形：按钮文案「快速匹配」→「`00:00` ×」，点击行为「开始匹配」→「取消匹配」；提示文字换成「正在寻找对手，点击按钮取消匹配」 |
| H3 | 位置不许变：idle 与 matching 两态下按钮的 `getBoundingClientRect()` 完全一致（`left/top/width/height` 差 ≤1px）；提示段落同样 ≤1px |
| H4 | 变形过渡 ≤150ms（背景色/宽度可过渡，但不得改变布局流）；按钮内「00:00」与「×」垂直居中，× 视觉 16px，点击区仍是整颗按钮 |
| H5 | 计时与底部全局匹配条同源（P25.1 的单一计时源规则不破） |
| H6 | 未登录时按钮隐藏并显示「登录后可快速匹配」（现状保留）；登录后位置与上面一致 |

## 2.7 I 件：底部匹配指示条要回来（但按钮内计时也保留）

**根因（`public/nav.js` 约 629–630 行）**：P26 为了让比赛页不再重复跳转，在 `pollMatchBar()` 开头加了

```js
if (page === "race") { clearMatchBar(); return; }
```

这行把**整条底部匹配条**在比赛页清空了——不只是跳转，连计时显示一起没了。而比赛大厅正是用户点「快速匹配」的地方，所以看起来"底部指示消失了"。

| # | 要求 |
| --- | --- |
| I1 | 比赛页**恢复底部匹配条**：`page === "race"` 时不再 `clearMatchBar()`，照常按 1 秒轮询 `/api/race/match/status` 并显示「匹配中 00:12」（或现有文案），**只跳过 `location.href` 跳转分支** |
| I2 | 比赛页的"进入比赛"由 `race.js` 自己处理（它已经在比赛页）：matched 时底栏显示「匹配成功，正在进入比赛…」，300ms 后隐藏，同时按钮复位、页面切到 `reveal` 视图 |
| I3 | **计时同源**：底部条与按钮内 `00:00` 必须读同一个起点（`raceMatchPendingSince` 或服务端 `elapsed`），任何时刻两个数字**完全一致**（不允许各走各的） |
| I4 | **取消同源**：点底部条 × 与点按钮，都调 `/api/race/match/cancel`，两边同时复位（底栏消失 + 按钮回「快速匹配」+ 提示文字回初始态） |
| I5 | 按钮设计保持不变（H 件：原地变形、位置差 ≤1px），底部条只是**额外**的指示，不得因为加了底栏而改变按钮布局 |
| I6 | 底栏高度变量 `--race-match-bar-h` 与页面底部留白照旧，不得让比赛大厅内容被遮挡 |

## 5. 停止点

- 若现成文章库里凑不出 3 篇满足字数区间的 → **停**，报可用数与长度分布，由我定放宽区间（不要自己拍）；

- 若关闭匹配房观战会影响 `findRoomBySpectator` 或"同一账号不能同时占两个房间"的判定 → **停**，先报影响面（这两处是 P20 加的，别顺手改坏）；
- 若 P26 的轮询修复还没落地（两台不会都跳转）→ **停**，先等 P26；
- 若你想顺手保留"玩家选择"能力 → **停**，那是另一批，本批只做系统随机。
