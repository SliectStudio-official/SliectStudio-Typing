## 2. 逐项交付

### A 组（先做，单独提交）：K-05 残留——改密/降权即失效

做法：给 `users` 加一列 `token_version`，token 里带上它，鉴权时比对。

| # | 位置 | 要求 |
| --- | --- | --- |
| A1 | `db-config.js` 两段建表 SQL 的 `users` | SQLite 加 `token_version INTEGER NOT NULL DEFAULT 0`；MySQL 加 `token_version INT NOT NULL DEFAULT 0` |
| A2 | `db-config.js` 的 `runMigrations` | 两个分支的迁移列表各补一条 `ALTER TABLE users ADD COLUMN token_version ... DEFAULT 0`（照现有写法，靠 try/catch 兼容已升级过的库）。**老库里所有用户默认 0，既有 token 因此仍然有效** |
| A3 | `server.js` 签 token 的**所有**位置 | payload 增加 `token_version: <库中值>`。至少 4 处：bootstrap 建管理员、注册、登录、`PUT /api/auth/me` 里因改用户名而重签的两条分支（那两处要用该用户当前的 token_version） |
| A4 | `server.js` 的 `authMiddleware` | 比对 `Number(decoded.token_version \|\| 0)` 与 `Number(row.token_version \|\| 0)`，不一致 → 401 `登录已失效，请重新登录`（与「用户不存在」区分开） |
| A5 | 自增点 | ① `PUT /api/user/password` 改密成功 ② `PUT /api/auth/me` 带 `newPassword` 改密成功 ③ `PUT /api/admin/users/:id` 改密码成功 ④ `PUT /api/admin/users/:id` **改 role 成功**（降权即失效）。四处都要 `SET token_version = token_version + 1`，与业务更新**同一条 SQL 或同一事务**，不许分两次写 |

A 组验收：

| 步骤 | 期望 |
| --- | --- |
| 老库启动（迁移） | 不报错；`PRAGMA table_info(users)` 里有 `token_version` 且老用户值为 0 |
| 登录拿 token A，然后改密码 | 改密 200；用 token A 访问 `GET /api/auth/me` → **401 `登录已失效，请重新登录`** |
| 用新密码重新登录 | 200，新 token 可用 |
| 用户被管理员从 admin 降为 user | 该用户手里的旧 token 访问 `GET /api/auth/me` → **401**；重新登录后 role 为 user |
| 管理员改别人的密码 | 被改者旧 token → 401；管理员自己的 token **不受影响**（只有目标用户自增） |
| 未改密的普通用户 | 旧 token 仍然**有效**（回归：本批不应造成全员掉线） |

### B 组（A 通过后，单独提交）：K-04 成绩上报准入与复算

| # | 位置 | 要求 |
| --- | --- | --- |
| B1 | `POST /api/leaderboard` | 登录用户的 `nickname` **忽略客户端传入值**，一律用库里的 `nickname`（为空则用 `username`）。匿名提交仍接受客户端昵称（游客榜需要） |
| B2 | 同端点，复算 | 当 `article_id` 有效且 `time_seconds > 0`：查该文章 `LENGTH(content)`，算理论速度 = 字数 ÷ (time_seconds / 60)（MySQL 用 `CHAR_LENGTH`）；与上报 `speed` 的偏差超过 **30%** → 400 `{ error: '成绩与文章长度不符，已拒绝' }`，并 `console.warn` 记一条（含 user_id、article_id、上报值与理论值） |
| B3 | 同端点，`article_id` 为空 | 允许提交，但 `source` 记为 `'unverified'`（便于事后筛） |
| B4 | `GET /api/leaderboard` | **总榜不再看 `allow_guest_leaderboard` 设置**：非 `?guest=true` 的查询恒加 `s.user_id IS NOT NULL`（匿名成绩只出现在 guest 榜） |
| B5 | `db-config.js` 的 `seedData` | 不再写入 `allow_guest_leaderboard` 这个键（已有库里若存在也不删、不读） |

B 组验收：

| 步骤 | 期望 |
| --- | --- |
| 登录用户提交真实成绩（按文章字数估的速度） | 200；库里昵称为该用户的昵称，不是客户端传的 |
| 登录用户刻意上报 999 分（文章 100 字、耗时 30 秒） | **400**；控制台有一条 warn |
| 匿名提交游客成绩 | 200；`GET /api/leaderboard`（不带 guest）**看不到**它；`?guest=true` 看得到 |
| 删除库里的 `allow_guest_leaderboard` 行后再查总榜 | 行为不变（已不再读取） |
| 回归 | P1 的 `COALESCE` 昵称覆盖修复仍生效（guest 榜昵称非空） |

### D 组（最后做，单独提交）：版本真值落地

| # | 位置 | 要求 |

| 步骤 | 期望 |

## 3. 数据准备与清理

1. 动手前把 `data/typing.db` 备份到 `tmp/`，报告写文件名。

## 4. 停止点

- 迁移在生产库上报错或出现半截状态 → 立刻停，用备份还原并贴读数，不要重试第二次
- 出现「既有 token 全部失效」→ 停（说明 A3/A4 实现与「老用户默认 0」不一致）
- 复算阈值把正常成绩大量误判 → 停，贴几条被拒的真实数据（字数、时长、上报值、理论值）再定
- 需要改 `VERSION` / `CONTRACT_VERSION` / `AGENTS.md` / `docs/adr/` → 停，这些归规划侧
- 需要动 `public/*.html`、`public/*.css`、`version.json` 的删除 → 停

## 5. 交付格式

四段式加执行报告，写进 `docs/reports/P9-执行报告.md`，第一行写 `docs/prompts/P9-安全补强.md` 的 sha256。报告必须含：

1. 改了什么：A/B/C/D 四组各一节。
2. 怎么验证：逐条贴读数（A 组必须贴「改密后旧 token 401」「降权后旧 token 401」「未改密用户的旧 token 仍 200」三条；B 组贴被拒那条的四个数字；D 组贴 `/api/version` 全文）。
3. 怎么回滚：四组各自改回哪几行；A 组额外写「迁移加了列，回滚代码后多出的列无害，不必删」；D 组写「恢复 `version.json` 读取逻辑」。
4. 不确定项：至少写「生产库迁移前后的 `table_info`」「复算阈值是否误伤」「MySQL 分支未实测」。
5. 数据结构与关系清单：**本批有变化**——`users` 新增 `token_version`，要单列给规划侧画图。
6. 上线提示：一句话说明「改密或改角色后，该用户的其它设备需要重新登录；其余用户不受影响」。
