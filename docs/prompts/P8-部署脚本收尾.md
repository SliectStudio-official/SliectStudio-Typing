## 2. 逐项交付

### A 组：K-11 首次进入生产模式时密钥没落盘

- 位置：`launcher.ps1` 第 2 阶段（First Start Wizard）。
- 现状：首次选生产模式时，向导生成的 `$launcherJwtSecret` 只存在内存里，`Write-ConfigFile` 只写了 `$launcherMode`；紧接着那段「补写密钥」的 `if` 条件是「变量为空」，而变量此时有值，所以**不触发**。结果：配置里没有密钥，下一次启动才补写——中间一次重启会把所有人踢下线。
- 改法：
  1. 抽一个 `Write-LauncherConfig` 函数：参数为 mode 与可选 secret；secret 有值时写两行（`$launcherMode`、`$launcherJwtSecret`），无值时只写 mode。
  2. 向导里选完模式后**一次写成**：生产模式 → 先 `New-RandomSecret` 再调用该函数（两行一起落盘）；开发模式 → 只写 mode。
  3. 保留「配置已存在但缺 secret 且模式为生产」的补写分支，作为兼容旧配置的兜底（行为与现在一致）。
  4. 其余阶段（Node 检测、npm install、端口选择、启动方式）**一行都不要动**。
- 验收口径：

| 步骤 | 期望 |
| --- | --- |
| 开工前把 `launcher.config.ps1` 备份到 `tmp/`，记录其 sha256 | 报告里贴出备份名与哈希（**不要打印密钥内容**） |
| 把 `launcher.config.ps1` 移走，模拟全新部署，跑向导并选「2 Production」 | 结束后 `launcher.config.ps1` 里**同时**有 `$launcherMode = 'production'` 与 `$launcherJwtSecret = '<64 位十六进制>'` |
| 再启动一次（配置已存在） | 密钥与上一轮**完全相同**，没有被重新生成 |
| 选「1 Quick Start (Dev)」在另一个临时目录试一次 | 只写 mode 行；服务端会自行生成 `data/jwt-secret.txt`（P3 的行为） |
| **还原现场** | 把备份的 `launcher.config.ps1` 放回，sha256 与动手前**逐字节一致**（贴前后两个哈希） |
| 脚本语法 | 用 PowerShell 解析器检查 0 个错误：`[System.Management.Automation.Language.Parser]::ParseFile('<绝对路径>', [ref]$null, [ref]$errors)` 后 `$errors.Count -eq 0` |
| 回归 | 阶段 1/3/4 的输出与改动前一致；`PORT` 逻辑未被改（P6 之后才真正生效，本批不动） |

向导是交互式的：可以用管道喂输入（`echo 2 | powershell -NoProfile -ExecutionPolicy Bypass -File .\launcher.ps1`），若管道下 `Read-Host` 拿不到输入，改为把 `Write-LauncherConfig` 与向导段落单独 dot-source 出来直接调用验证，**但必须在报告里写明你用的是哪种方式、以及为什么**。
