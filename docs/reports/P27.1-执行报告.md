# P27.1 执行报告：候选不足修正

- 执行方：执行方 AI；日期：2026-11-07
- 提交：`4a9b675 fix: 匹配候选不足自适应抽文`
- 环境：Node v25.3.0；沙箱 `tmp/p271-app`（生产库副本，端口 3086）；Chrome 156 headless + CDP
- 口径裁定（用户 2026-11-07 拍板）：候选池**只收 100–800 字**；72 字《经典诗词》不参与匹配。该裁定覆盖 A2 的「所有 approved 非空」字面口径。

## 1. 改了什么

| 文件 | 改动 |
| --- | --- |
| `server.js` | `attemptMatch`：approved 且 100–800 字、正文非空的文章进入池；200–400 优先、其余 100–800 按原顺序稳定排在后面；`candidates = pool.slice(0, min(3, pool.length))`；不足 3 时打 `[匹配] 候选不足 三篇→N 篇`；空池返回 `暂无可用文章，请稍后再试`；`createMatchedRoom` 计算 `resolution`（three/two/single），single 的 `revealEndsAt = now+800`，two/three 仍 1500；`race.reveal` 与快照增加 `resolution` |
| `public/race.js` | 抽文视图按 `candidates.length` 自适应；key 带 resolution；单卡分支不做轮转，直接淡入居中添加 winner；single 的轮询间隔 300ms，two/three 仍 600ms |
| `public/style.css` | 单卡 `is-single` 居中放大；420px 单卡 winner scale 1.04；两张/三张沿用原布局 |

没有改数据表、`VERSION`、`CONTRACT_VERSION`、P28 引导页样式，也没有改 P29 的解散规则。`public/race.html` 未改。

### 七条验收读数

**1. 真实库能配对（生产库副本）**

```json
JOIN_A: {"status":"waiting","waiting":1,"elapsed":0}
JOIN_B: {"status":"matched","code":"MRD7U2"}
TICK_A: {"status":"reveal","matchmade":true,
  "candidates":[{"articleId":9,"charCount":281},{"articleId":2,"charCount":245}],
  "resolvedArticleId":9,"resolution":"two","remainMs":1495}
TICK_B: 同房间，status=reveal，resolution=two，resolvedArticleId=9，remainMs=1492
```

- `candidates.length = 2`，两篇互不相同，均为 100–800 字。
- 服务端日志：`[匹配] 候选不足 三篇→2 篇`。
- 两台 tick 的 `resolvedArticleId` 与 `resolution` 完全一致。

**2. 两卡抽奖**

- 候选 id：`9, 2`；resolved：`9`。
- 高亮采样（页面内 50ms 采样，时间相对 reveal 开始）：

```text

t=548 id=9, t=648 id=2, t=798 id=9, ...（两张卡交替）
```

- 落定：`winnerId=9`，与 `resolvedArticleId=9` 一致；页面卡片数=2，`is-single=false`。
- 截图：[P27.1-two-card.png](P27.1-two-card.png)
- 说明：为方便采样，该前端测试把**沙箱副本** reveal 时长临时设为 4000ms；源码 two 仍 `REVEAL_DURATION_MS=1500`，生产副本 API 读数为 `remainMs=1495`。

**3. 单卡场景**

- 源码行为（生产库副本只留 id=2 approved）：B join → matched，tick：

- 950ms 后 tick：`status=countdown`，`startsIn=2836`，说明 800ms 后已进入倒计时。
- 前端（沙箱把单卡 reveal 临时延长到 4s 以截取首屏）：卡片数=1、`is-single=true`、高亮采样数组为空（无轮转）、winner id=2、居中差=0px、transform `matrix(1.12, 0, 0, 1.12, 0, 0)`、可见卡=1。
- 截图：[P27.1-single-card.png](P27.1-single-card.png)
- 源码单卡时长仍为 800ms。

**4. 空池场景**

- 沙箱副本把 approved 全部置 pending 后重启；新用户：

```json
JOIN_A: {"status":"waiting","waiting":1}
JOIN_B: {"status":"waiting","waiting":2,"hint":"暂无可用文章，请稍后再试"}
ACTIVE_A: {"code":null}
ACTIVE_B: {"code":null}

```

- 服务端日志：`[匹配] 候选不足 三篇→0 篇`；没有 `[匹配] 配对成功`；未创建房间（重启后 activeRoomCount=0，join 后仍无房间）。
- 说明：两个用户仍以 waiting 留在匹配队列（可取消），与现有 join 语义一致；若 A4 的「不得留在队列」是指**立即出队**，需要再改 join/状态机（见 §4）。

**5. 三卡回归**

- 沙箱副本补入一篇 300 字 approved（id=16），新用户配对：


**6. 同局一致**

- two / single / three 三种房间的两端 tick 均为 `same=true`：`resolvedArticleId` 与 `resolution` 完全相同。

## 3. 怎么回滚

手动恢复：

1. `server.js`：恢复 `attemptMatch` 原来的「preferred/fallback + 必须≥3」选择，删除 `resolution`/single 800 逻辑，`revealView` 去掉 resolution。
2. `public/race.js`：恢复 reveal key 与统一 1500ms 四段动画（删除 `is-single` 分支与 single 300ms 轮询）。
3. `public/style.css`：删除 P27.1 的 `.is-single` 三条规则。
4. 无表结构、`VERSION`、`CONTRACT_VERSION` 改动，无需迁移。
