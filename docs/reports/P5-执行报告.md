### 未通过的验收项：资产变化时的自动缓存轮换

提示词要求“临时改 `theme-toggle.js` 后重启并刷新页面 → 出现新名字的 cache，旧名字的 cache 被清掉”。实测**未自动发生**：

1. 临时再次修改 `theme-toggle.js`（版本变为 `351b881f14c8`、该文件哈希 `75b67bd2`），重启服务后正常刷新 `admin.html`。
2. Cache Storage 结果：`typing-7ebb358db891` 与 **`typing-fallback`** 并存；**没有** `typing-351b881f14c8`，旧 `typing-7ebb358db891` 也未被删除。
3. 原因：只改资源时 `service-worker.js` 字节未变，浏览器更新检查不会触发新的 install/activate；`CACHE_NAME` 只在 install 中赋值，SW 被浏览器回收后重启时模块级 `let` 回到初始值 `typing-fallback`，运行期缓存因此写入 `typing-fallback`。
4. 强制注销 SW 并清空缓存后重新注册（等价于一次全新 install），得到 `typing-351b881f14c8`，旧缓存被 activate 清理——说明 B1/B2/B3 在 install 真正运行时逻辑正确。

结论：在线新鲜度目标仍由 A 组的 HTML 重写（导航网络优先）+ 带哈希 URL + SW 网络优先策略保证；但“资源变化自动轮换 cache 名并清理旧 cache”这一条在现有设计下无法自动触发，需要后续决定（例如给 SW 注册 URL 带版本、由服务端向 SW 脚本注入版本，或调整 SW 启动时的缓存名恢复策略）。本批按提示词实现，未自行扩大设计。
