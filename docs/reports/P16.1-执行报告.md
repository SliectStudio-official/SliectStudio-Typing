# P16.1-分段偏移收口 执行报告

两组分开提交：

| 组 | 提交 | 内容 |
| --- | --- | --- |
| A | `35bf71f` | `typing-engine.js`：导出 `splitTextWithOffsets`，引擎 `offsetOf` 改读真实原文下标，`restore` 使用该偏移 |
| B | `050cc05` | `script.js`：首页 `segmentOffsets`、进度、`charStates`/朗读索引与错字上报按原文坐标 |

## 一、改了什么

### A 组（`public/typing-engine.js`）

- 新增 `window.TypingEngine.splitTextWithOffsets(text, maxLen) → { segments, offsets }`：
  - 先调用原有 `splitTextIntoSegments`，**分段结果不变**；
  - 按原文顺序对齐每段：跳过的 `\n`、空格计入段间空隙，`offsets[i]` 是第 i 段首字符在原文中的真实下标；
  - 保留原 `splitTextIntoSegments` 导出。
- `create()` 内部改为 `var split = splitTextWithOffsets(text)`，`offsetOf(index)` 直接返回 `offsets[index]`，不再累加段长。
- `restore(typedCount)` 沿用 `offsetOf(i)` 写 `charStates`，因此恢复时写入的是原文坐标；段/段内位置仍按服务端 `progress`（已输入字符数）定位。

### B 组（`public/script.js`）

- 新增 `segmentOffsets` 状态；`startPractice()` 改为：
  `const split = window.TypingEngine.splitTextWithOffsets(originalText)`，取 `segments` 与 `offsets`；reset 时清空。
- `getSegmentStartOffset(i)` 改为 `return segmentOffsets[i] || 0`，不再累加 `segments[i].length`。
- 全文模式进度改为：
  `(segmentOffsets[currentSegment] + inputValue.length) / originalText.length * 100`；
  最后一段输入完成时直接置 100%，`finishPractice()` 也兜底置 100%。
- 错字上报改为逐段配对：遍历 `segments[i]` 的每个字符，用 `charStates[offsets[i] + k] === 'wrong'`，写 `expected_char: segments[i][k]`、`typed_char: segmentInputValues[i][k]`。
- `charStates` 渲染、`updateSegmentStates` 的 offset、`getCurrentWord(globalPos)` 全部使用真实偏移；计分/计时/准确率/朗读开关/结算卡未改。

## 二、怎么验证

环境：`tmp/p161-app`，生产库 `data/typing.db` 的只读 backup 副本，端口 **3080**；测试账号 `__verify_p161`。页面用 headless Chrome + CDP 合成输入；生产库/生产 3000 端口未写。

### 1. 281 字文章全文进度

文章 id=9《Token(词元)是什么》，原文 **281** 字。分段 offsets：

```
segments 长度 = [10,27,35,24,29,15,26,33,21,29,21]
offsets       = [0,11,38,75,100,131,147,174,209,231,260]
末段结束     = 260 + 21 = 281
```

| 读数 | 值 |
| --- | --- |
| 开始前 `#text-progress.style.width` | 空字符串（尚未开始，全文模式进度条未设置） |
| 到第 5 段后、当前第 5 段输入 2 字 | 当前段索引 **5**，`segmentOffsets[5]=131`，输入 **2**；计算 `(131+2)/281=47.330960…%`；界面 `47.331%` |
| 全文最后一段输入完成 | `#text-progress.style.width = **100%**` |
| 结算卡 | `typed=270`、`correct=270`、`accuracy=100%`、`speed=2843 字/分`（用时由本次自动输入速度决定） |

> 结算后输入卡隐藏，`getBoundingClientRect().width` 为 0，因此这里按提示词允许的 `style.width` 取值；`100%` 是实际宽度值。

### 2. 错字上报请求体（换行前后各一处）

在第 1 段（`Token...`，原文下标 0）敲 `X` 代替 `T`，在第 2 段（换行之后第一段，offsets[1]=11）第一个字敲 `错` 代替 `你`。为了保留两个错误状态到结算，测试在两次错误输入后调用 `moveToNextSegment()` 进入下一段（正常交互下错误字符不会自动翻行；这是测试夹具的显式推进，见不确定项）。

页面捕获到的 `/api/user/error-log` 请求体原文：

```json
{"article_id":9,"errors":[{"expected_char":"T","typed_char":"X"},{"expected_char":"你","typed_char":"错"}]}
```

位置核对：

- 第 1 处：`originalText.slice(0,6) = "Token "`，`expected_char=T`，实际 `typed_char=X`；
- 第 2 处：`segmentOffsets[1]=11`，`originalText.slice(8,16) = "元)\n你有没有好"`，其中下标 11 的字符是 **你**；请求体 `expected_char=你`、`typed_char=错`，配对正确；Network/资源记录 `/api/user/error-log` 请求数 **1**。

- 朗读索引：`segmentOffsets[1]=11`，从该段内定位到 `Deepseek`（原文位置 23），`getCurrentWord(23)='Deepseek'`，上下文 `，当你向 Deepseek、豆包、千`；headless 没有播放音频，只验证索引函数。

## 四、不确定项

1. **错字测试的推进方式**：正常输入下错误字符不会自动翻段，所以测试用页面上下文显式调用 `moveToNextSegment()`，保留错误 `charStates` 到 `finishPractice`。请求体与配对逻辑是真实的；但“正常用户一路敲错再完赛”在界面流程上不会自然发生，这是现有错误上报触发点的既有行为。
2. **全部交互为 headless Chrome + CDP 合成键入**，不是真人键盘；`#text-progress` 结算后因输入卡隐藏 rect 为 0，只能用 `style.width=100%`。
3. **朗读只验证了索引函数**：headless 无音频输出，也没有可观测的“高亮词”视觉元素；“当前词”是直接调用 `getCurrentWord` 与原文片段比对。
4. **比赛页只验证了比赛中进度与刷新恢复**，没有把两名选手完整跑到终点；比赛完赛的满值逻辑仍沿用服务端 `charCount`，本批未改。
5. **数据来源**：281 字文章从生产库只读 backup 副本读取，未改生产库；偏移/错误配对样例是真实文章内容，错误字符是测试构造。
6. **分段算法本身仍会 trim 换行与行尾空格**（P16 规则），因此 `segments` 拼接 270 字、原文 281 字是预期；offsets 把这 11 个空隙计入原文坐标，不改变分段结果。
