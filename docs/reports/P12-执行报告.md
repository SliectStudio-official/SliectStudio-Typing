## 1. 改了什么

### 数据表（db-config.js，SQLite/MySQL 两套）

- `races`：`id, code(UNIQUE), cancelled_reason, cancelled_by, password_hash, host_user_id, article_id, article_title, content_snapshot, char_count, status, is_public, max_players, player_count, started_at, finished_at, created_at`；status 索引。
- `race_participants`：`id, race_id, user_id, guest_id, nickname, is_guest, ready, progress, speed, accuracy, time_seconds, rank_no, finished_at, joined_at`；外键 `race_id → races ON DELETE CASCADE`、`user_id → users ON DELETE CASCADE`；唯一索引 `(race_id, user_id)` 与 `(race_id, guest_id)`；自增 id 解决游客 NULL 主键问题。
- 新表用 `CREATE TABLE IF NOT EXISTS`，老库启动自动建，无需 ALTER。

### 内存房间与服务端（server.js）

- `roomRegistry`（code → room），房间状态/进度/准备/倒计时只在内存；数据库只在建房、开赛、结束、取消时写。
- `raceAuth`：真实用户复用现有 `authMiddleware`（含 token_version 校验）；游客 token 校验 `role='guest'`、`raceCode` 与房间内 `guestId`；`authMiddleware` 增加拒绝游客 token。
- 参赛端 10 个：`create / join / leave / ready / kick / start / tick / finish / list / :code`；管理端 5 个：`GET /api/admin/races`、`cancel`、`kick`、`GET/PUT /api/admin/race-settings`。
- 建房：必须登录、4 位数字密码 bcrypt 哈希、6 位房间码（31 字符表、内存+库双查重 10 次）、容量上限、`race_enabled` 开关。
- 加入：公开房/密码房、`ip|code` 5 次失败/10 分钟限流、游客昵称归一化与自动序号、每房游客≤4、同 IP 同房 1 个游客席位、满员/非 waiting 拒绝、重连幂等。
- 开赛：全员准备、正文快照与字数/人数/时间写库、`countdown` + `startsAt=now+3000`。
- tick：一次往返上报进度（只增不减、≤字数）+ 返回快照；快照带 `serverNow`、`cancelledReason`。
- finish：服务端计时算速度、写 `scores`（`race` / `race_guest`）与 `race_participants`，全员完赛自动 `finished`。
- 清理定时器 30 秒：等待 2 小时取消、房主 5 分钟无心跳取消、比赛中字数×2 分钟到时结束、finished/cancelled 房间 60 秒后移出内存；`process.on('exit')` 清理 `setInterval`。
- 启动时把库里 `racing`/`countdown` 行改为 `aborted`。
- 数据库面板白名单增加 `races` / `race_participants`，使管理员可在既有 DB 面板查看/删除（`password_hash` 仍由 P4 敏感列过滤）；生产测试房间归档行即通过该接口删除。

## 3. 怎么回滚

- 删除 `server.js` 的 race 常量/注册表/helpers/`raceAuth`/15 个端点/清理定时器/启动 abort 调用；删除 `authMiddleware` 的 guest 拒绝分支；从 `ALLOWED_TABLES` 去掉 `races`、`race_participants`。
- `db-config.js` 的两张新表可保留（旧代码不读，不影响的运行），无需 DROP。
- `settings` 的 `race_max_rooms` / `race_enabled` 未在生产写入，回滚无数据残留。
- 生产库已建的空白表可保留；如需彻底清理需另行批准 DROP。

## 4. 不确定项

1. **MySQL 分支未实测**：建表、`ON DUPLICATE KEY UPDATE`、`CHAR_LENGTH` 只做代码核对。
2. **并发上限未压到极限**：只测 8 人房 ×20 tick（160 请求），未压 100 用户/84 req/s 软上限。
3. **房间码碰撞重试次数**：31^6 组合，10 次重试未真实撞过；未做压力碰撞验证。
4. **生命周期时间路径**：host_disconnect 5 分钟路径实际触发；2 小时未开赛、字数×2 分钟到时结束未等到真实触发（阈值太长），代码已实现但未实测。
5. **合成成绩速度**：验收中比赛被压缩到 2 秒完成，finish 算出 speed≈6203，超过常理；服务端计时与写库正确，但 spec §7 的「>1200 标记 suspect」未在本批实现（P12 提示词未要求）。
6. **3000 端口**：被规划侧 P11 预览占用，生产单房验证走 3071（P6 `PORT` 支持）；P12 代码尚未在 3000 进程加载，需要重启 3000 预览才能提供比赛端点。
7. **K-25**：`/api/user/stats` 当前已是 200（路由只传 user_id，规划侧已修）；本批未改该路由。
8. **契约版本**：`CONTRACT_VERSION` 仍 v2，新表属结构变更；按 P12 提示词未改版本/ADR，等规划侧升 v3 并补 ADR。
9. **临时沙箱**：`tmp/p12-app/`、P12 测试脚本保留在 `tmp/`（gitignored，进程已停）；生产库测试对象已清零。
