# 设计四问模板（每个新功能必答）

> 用户 2026-11-07 要求：**以后每个功能都按这个思路想——怎么分类？怎么设计？怎么做？是否有真实参考？**
> 用途：规划侧收到需求后，先按本模板答完四问，再出提示词。四问没答完不许开工。
> 位置：`docs/设计四问模板.md`；在 `AGENTS.md` §2 表里登记为规格来源之一。

---

## 一、怎么分类（先定性，再谈做法）

| 判据 | 要回答的问题 |
| --- | --- |
| 层 | 纯前端？纯后端？两端？还是**数据/契约**级？ |
| 影响面 | 动哪几个文件、哪几个模块、哪几条既有验收会失效 |
| 数据 | 要不要新表 / 新字段 / 新设置项？如果需要 → 触发 `CONTRACT_VERSION` + §5.5 + ADR，先报批 |
| 依赖 | 能不能只用白名单依赖 + 标准库做完？需要 WebSocket/SSE/第三方库吗（本项目禁止） |
| 状态归属 | 状态放哪：进程内存（单进程前提）／SQLite／localStorage／sessionStorage |
| 可逆性 | 回滚是"改一个值"还是"删一张表/一条迁移" |

**输出格式**：一句话定性 + 一张"影响面表"（文件 / 端点 / 数据 / 验收项）。

## 二、怎么设计（把规则、边界、失败态写死）

必须逐项写出，缺一项就回来问：

| 项 | 内容 |
| --- | --- |
| 用户目标 | 用户点一下想得到什么（一句话） |
| 状态机 | 有哪些状态、怎么流转、哪些操作在哪个状态被禁止 |
| 容量与上限 | 人数、房间数、队列长度、席位数的**具体公式**与夹紧区间 |
| 权限 | 谁能看、谁能改、房主/管理员/游客/选手/观战者的差异 |
| 失败态 | 每一种失败给什么文案、什么状态码；**失败必须可见**，不许渲染成正常结果 |
| 边界 | 满员、空集、超时、断线、重启、并发双击、页签关闭 |
| 一致性 | 与既有功能冲突吗（例如"排队中又自己建房"→ 自动取消排队） |
| 不做清单 | 明确写"本批不做 X"，防止范围膨胀 |

## 三、怎么做（落到可验收的颗粒）

| 项 | 内容 |
| --- | --- |
| 端点 | 路径 / 方法 / 鉴权 / 入参 / 返回形状 / 状态码 |
| 数据 | 内存对象字段 or 表结构（含默认值） |
| 前端 | 放在哪个页面哪个区块、有哪些控件、三态（等待/成功/失败） |
| 视觉 | 用哪些**令牌**（禁止写死颜色，K-34）；亮暗两套主题都要过 |
| 验收 | 每条判据必须是**能读到数字或字符串**的（如"对比度 ≥ 4.5:1""恒等式成立""404 且 content-type 是 JSON"），不写"看起来正常" |
| 回滚 | 按组列出：改哪个文件、恢复成什么 |
| 并行冲突 | 若与在队的批次同改一个文件 → 写明先后顺序与合并原则 |

## 四、是否有真实参考（能查到就引，查不到就说查不到）

**我这边的能力边界（2026-11-07 实测）**：

| 能不能 | 实测 |
| --- | --- |
| ✅ 抓官方文档 | MDN `developer.mozilla.org` 200 |
| ✅ 读 GitHub 仓库/Issue/源码 | `api.github.com` 200、`raw.githubusercontent.com` 200 |
| ✅ 查 npm 包元数据 | `registry.npmjs.org` 200 |
| ❌ 搜索引擎 | 无搜索接口；`duckduckgo.com` 超时 |
| ❌ 部分站点 | `en.wikipedia.org` 连接失败 |

**所以"真实参考"这一栏这么写**：

| 情况 | 写法 |
| --- | --- |
| 抓到了原文 | 给出**产品/规范名 + URL + 它怎么做的 + 我们采纳哪点、为什么不采纳其余** |
| 只有通用知识、抓不到原文 | 明写「凭通用认知，未取到原文」，并说明依据的是哪类产品的常见做法 |
| 完全没参考 | 写「本项目自定，理由：…」——不要编造出处 |

**参考要落在"决策"上**，不是凑字数：每条参考都必须对应一条我们要么采纳、要么明确不采纳的规则。

## 五、示例（P20 观战席，四问走一遍）

| 问 | 答 |
| --- | --- |
| **分类** | 两端 + 纯内存状态。动 `server.js` 观战段、`race.html`、`race.js`、`style.css`；不动表结构（席位、模式都放 room 对象）→ 不需要升 `CONTRACT_VERSION` |
| **设计** | 状态机：`waiting` 可换席，`countdown`/`racing` 禁止；容量 `cap = max(1, floor(maxPlayers×0.1))`，房主可设 1..cap；两种模式 `free`/`host`；房主进观战席保留管理权；全员观战则禁止开赛 |
| **怎么做** | 3 个端点（settings/self/assign）+ 快照加 `mySeat`/`spectatorSeats`；前端两栏 + 观战席面板；验收 13 条含"8 人房设 2 席必须被拒" |
| **参考** | Typeracer / 10FastFingers 的"比赛中可围观"是**只读观众**、无席位概念；电竞/棋类赛事（challonge、chess.com 赛事）是"主办方分配席位"——我们据此把 `host` 模式作为"真实比赛"分支。**注意**：这两个站点我抓不到原文，属通用认知，未引用具体页面 |

## 六、硬规矩

1. 四问没答完 → 不出提示词；
2. 每条规则都要有**可验证判据**（数字或字符串），不写"合理即可"；
3. 参考栏不许编造出处；抓不到就说抓不到；
4. 设计里出现"要不要…"的岔口 → 进 `docs/待拍板问题清单.md`，并给默认值，不许自己拍；
5. 结论落进 `docs/specs/` 对应规范，提示词只做"怎么交付"，不重复长篇设计。
